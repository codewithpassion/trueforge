- JSON projection aliases MUST be listed in `jsonColumns.ts`'s `JSON_RESULT_COLUMNS`.
- Kysely's SqliteAdapter keeps `supportsTransactionalDdl: false`, so Migrator does not wrap migrations. Every `up`/`down` that touches the schema MUST open `db.transaction()` itself. `PRAGMA foreign_keys` is a no-op inside a transaction — toggle it outside the txn when rebuilding a referenced parent (see kysely#56).
- Every new `migrations/*.ts` MUST ship a matching SQL file under `packages/trueforge/migrations/d1/`: a new numbered file with only the delta once any D1 database is deployed; regenerate `0001_init.sql` with `pnpm d1:schema:dump` only while none is. D1 migrations are not transactional, so multi-statement rebuilds MUST use `PRAGMA defer_foreign_keys = true`.
- Stores here run on better-sqlite3 and D1. Store modules MUST NOT import `client.ts` (better-sqlite3); runtime-neutral helpers live in `errors.ts`, `jsonColumns.ts`, and `sqlExpressions.ts`.
- Multi-write store methods MUST use `AtomicRunner.batchWrite` with the conditional chain: statement 1 is the guarded write, and every later statement re-checks that guard in SQL (for example `WHERE EXISTS` on the row statement 1 wrote). A plain `WHERE` guard followed by unconditional writes commits on D1. `withTransaction` gives no atomicity on D1.
- Store SQL MUST NOT expand placeholder lists or multi-row `VALUES` from input; bind one JSON array and read it with `json_each` (`jsonListValues`). D1 rejects statements with more than 100 bound parameters.
- D1 limits a single string, BLOB, or row to 2,000,000 bytes, and `chunkJsonRows` never splits one row. Callers MUST keep each context message, event, and JSON document under that size; the store does not map the D1 error to a domain error, and local D1 (miniflare) does not enforce the limit, so tests cannot catch a violation.
- The context mapping's `ORDER BY append_id DESC LIMIT N` relies on batches running alone (better-sqlite3 connection mutex, serial D1 batches), so it MUST stay in the same batch as its log insert.
