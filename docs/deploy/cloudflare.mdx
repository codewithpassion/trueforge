TrueForge can run on Cloudflare Workers instead of a Node server. The agent features work the same way, except for Code Mode, which is not available yet. Code execution and skills run in a Cloudflare Container, one per session, and are switched on with `TRUEFORGE_SANDBOX_BACKEND`.

The Workers setup is deployed from a clone of this repository. Commands below run from the repository root unless a step says otherwise.

## What runs where

| Part | Role |
| --- | --- |
| Worker | Serves the HTTP API and checks login on every request. |
| Static assets | Serve the chat UI from `/`. A browser navigation to any other page gets the UI. Requests for files that do not exist get `404`. |
| `SessionDO` (Durable Object) | Runs turns, one object per session. Holds the event log of running turns, serves `subscribe` streams, and handles cancel. |
| `SchedulerDO` (Durable Object) | One instance. Its alarm checks for due scheduled runs every 60 seconds and starts them in `SessionDO`. A cron trigger every 5 minutes re-arms the alarm, for example after a deploy. |
| `ComputerDO` (Durable Object) | One per session while code execution is on. Owns that session's `/workspace` in its own SQLite storage and runs commands in a Cloudflare Container. |
| D1 | Stores sessions, turns, agents, schedules, and settings. |

## Prerequisites

- A Cloudflare account on the **Workers Paid** plan. The Free plan has daily D1 row limits and a CPU time limit that long turns exceed. The Worker sets `limits.cpu_ms` to 300000 (5 minutes), which needs the Paid plan.
- Node.js 22.14 or newer, [pnpm](https://pnpm.io), and [Bun](https://bun.sh). Package scripts run Wrangler 4.131.2 with `bunx`. The one-off commands below use `bunx wrangler`; add `@4.131.2` if you want the same version.
- An OIDC identity provider. Workers do not support the no-login mode. See [Setup Login](/authentication/overview) to register a confidential (Web) app.

Install dependencies and log in to Cloudflare:

```bash
git clone https://github.com/truefoundry/trueforge && cd trueforge
pnpm install
bunx wrangler login
```

## Deploy

<Steps>
  <Step title="Create the D1 database">
    Choose a location hint close to where your agents' model and tool traffic goes. Every turn event is a D1 write, so distance adds latency to each one.

    ```bash
    cd packages/trueforge
    bunx wrangler d1 create trueforge --location weur
    ```

    Location hints are `wnam`, `enam`, `weur`, `eeur`, `apac`, and `oc`. The command prints a `database_id`.

  </Step>

  <Step title="Set the database id">
    In `packages/trueforge/wrangler.jsonc`, replace the placeholder `database_id` with the printed value. Keep `binding`, `database_name`, and `migrations_dir` as they are.

    ```jsonc packages/trueforge/wrangler.jsonc
    "d1_databases": [
      {
        "binding": "DB",
        "database_name": "trueforge",
        "database_id": "<your-database-id>",
        "migrations_dir": "migrations/d1",
      },
    ],
    ```

  </Step>

  <Step title="Configure OIDC">
    Set the non-secret values in `vars` in `wrangler.jsonc`. `PUBLIC_BASE_URL` is the origin users open, with no path. Register `<PUBLIC_BASE_URL>/api/v1/auth/callback` as the redirect URI with your identity provider.

    ```jsonc packages/trueforge/wrangler.jsonc
    "vars": {
      "TRUEFORGE_RUNTIME": "workers",
      "OIDC_ISSUER_URL": "https://login.example.com/oauth2/default",
      "OIDC_CLIENT_ID": "<client-id>",
      "PUBLIC_BASE_URL": "https://trueforge.example.com",
    },
    ```

    The optional `OIDC_*` claim and scope variables from [Setup Login](/authentication/overview) go in `vars` too. Store the client secret as a Worker secret, from `packages/trueforge`:

    ```bash
    bunx wrangler secret put OIDC_CLIENT_SECRET
    ```

    <Warning>
      Never put secrets in `vars`. `wrangler.jsonc` is committed, and `vars` are visible in the Cloudflare dashboard.
    </Warning>

    The Worker does not start unless `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, and `PUBLIC_BASE_URL` are all set, and `wrangler deploy` rejects it. `pnpm workers:check` does not catch a missing value, because its startup check runs without vars or secrets. If `TRUEFORGE_RUNTIME` is not `workers`, every API request returns `500`. For more protection, put [Cloudflare Access](https://developers.cloudflare.com/cloudflare-one/policies/access/) in front of the Worker as well.

  </Step>

  <Step title="Deploy">
    From the repository root:

    ```bash
    pnpm workers:deploy
    ```

    This builds the UI into `packages/trueforge/dist-workers-assets`, applies D1 migrations to the remote database, and deploys the Worker with both Durable Objects. Run the same command for every later deploy.

  </Step>

  <Step title="Sign in">
    Open `PUBLIC_BASE_URL`. You are sent to your identity provider. After sign-in, admins add model providers and MCP servers under **Settings**, the same as on a Node deployment. Provider API keys are stored in D1, not as Worker secrets.
  </Step>
</Steps>

To check the build without deploying, run `pnpm workers:check`. It builds the UI and the Worker bundle, and reports the bundle size and the local startup time.

## Local development

Local development uses `wrangler dev` with a local D1 database.

1. Create `packages/trueforge/.env` with the OIDC settings for a test app at your identity provider. Wrangler reads this file and its values replace `vars`. Do not use `.dev.vars`.

   ```bash packages/trueforge/.env
   OIDC_ISSUER_URL=https://login.example.com/oauth2/default
   OIDC_CLIENT_ID=<client-id>
   OIDC_CLIENT_SECRET=<client-secret>
   PUBLIC_BASE_URL=http://localhost:8787
   ```

   Wrangler passes every key in this file to the Worker. Leave `STANDALONE` and the `*_CATALOG_PATH` variables out of it. Register `http://localhost:8787/api/v1/auth/callback` as a redirect URI on the test app. `pnpm workers:dev` listens on port 8787 unless you pass `--port`; if you do, use that port in the redirect URI and in `PUBLIC_BASE_URL`.

2. Apply migrations to the local database and start the Worker:

   ```bash
   pnpm d1:migrate:local
   pnpm workers:dev
   ```

3. Open [http://localhost:8787](http://localhost:8787).

To run the scheduled handler on demand during local development, call:

```bash
curl "http://localhost:8787/cdn-cgi/local/scheduled"
```

## Code execution and skills

Set `TRUEFORGE_SANDBOX_BACKEND` in `vars` to offer the built-in sandbox on this deploy:

```jsonc packages/trueforge/wrangler.jsonc
"vars": {
  "TRUEFORGE_SANDBOX_BACKEND": "cloudflare-computer",
},
```

Deploy, then turn it on per tenant: **Settings → Sandbox providers → Cloudflare Computer → Enable**. There is no form and no API key. **Disable** on the same row turns it back off, after a confirmation; workspaces already running are discarded with their sessions. Enabling is what switches on the `exec` tool, skills, non-inline file uploads, and turn file downloads; `GET /api/v1/capabilities` reports sandbox and skills as enabled from that point, and the UI shows them.

<Warning>
  **Upgrading a deploy that already sets `TRUEFORGE_SANDBOX_BACKEND`.** The variable used to be the whole switch; it now only offers the provider. After upgrading, the sandbox is off until an admin clicks Enable, and until then a saved sandbox-enabled agent answers `422` with "no sandbox provider is configured". One click per tenant restores it; nothing else needs changing.
</Warning>

Each session gets its own container-backed `/workspace`, which persists for the life of the session and survives an idle container, because the Durable Object's SQLite storage is the authoritative copy. Skills are downloaded into `/workspace/.trueforge/skills` on the first sandbox use of each turn, and a skill the agent no longer asks for is removed there on the next turn.

Daytona is not offered on Workers — its provider cannot run there — so the sandbox provider catalog lists only the built-in entry, and a `PUT` of a Daytona manifest returns `422`. With the variable unset nothing is offered at all: the catalog is empty and both `GET` and `PUT` behave as they did before the built-in sandbox existed.

<Warning>
  Cloudflare Computer is a preview and its own README says it is not ready for production. Leave `TRUEFORGE_SANDBOX_BACKEND` unset if that matters to you.
</Warning>

The `containers` entry in `wrangler.jsonc` is what provisions Cloudflare Containers, and it does so on the next `wrangler deploy` whether or not the variable is set. Unsetting the variable switches the feature off; removing the `containers` entry is what stops the provisioning and the image push. `pnpm workers:check` and `pnpm workers:deploy` both build the container image, so both need Docker and anonymous pull access to `ghcr.io`.

`max_instances` in the same entry bounds how many sessions can run a container at once. Past it a turn reports that no sandbox could start and asks the caller to retry; the session's workspace is untouched and a later turn works normally. Containers also stay warm for about 10 minutes after their last command, so a session holds its slot past the turn that used it.

## Not supported on Workers

| Feature | What callers see |
| --- | --- |
| Code Mode | Not available. The model calls MCP tools directly instead, and the in-sandbox client is not installed. |
| Sandbox and skills before the built-in provider is enabled | Reported as disabled in `GET /api/v1/capabilities`. A sandbox-enabled agent spec gets `422` with "no sandbox provider configured", and a non-inline file upload gets `422` with code `agent_sandbox_required`. Turn file downloads return `412`. |
| Daytona sandbox providers | Not offered in the catalog; a `PUT` of a Daytona manifest returns `422`. |
| Deleting a configured skill | The settings skills API has create and replace only, so a skill stays in the tenant list once added. |
| Session import | Returns `500` with "Session import requires Postgres". |
| TrueFoundry mode | Rejected at startup. Setting `TRUEFOUNDRY_SERVICEFOUNDRY_SERVER_URL` stops the Worker from starting. |

## Known limits

- **Turns do not survive restarts.** A turn runs inside its `SessionDO`. If Cloudflare evicts the Durable Object or you deploy while a turn runs, the turn stops. A watchdog alarm later marks it as abandoned. Start a new turn to continue the session.
- **A deploy stops running turns.** A deploy resets the Durable Objects, so a turn still running at that moment ends as cancelled, and its recorded reason may be `client-cancelled`. Deploy between turns where you can.
- **Long turns hand over every 14 minutes.** The `SessionDO` alarm keeps each turn running, including turns started with `stream: false` and scheduled runs. One alarm run lasts at most 14 minutes; a longer turn continues in the next alarm run.
- **D1 query budget per turn.** D1 allows 1000 queries per Worker invocation on the Paid plan, and a turn runs within one invocation. On local D1, a single-thread turn with small tool results used about 8.2 D1 statements per tool iteration: 99 tool iterations used 814 statements. The server logs a warning at 800. The default limit of 100 tool iterations ends such a turn at about 818 statements, so the risk comes from sub-agents, compaction, larger tool results, or a raised iteration limit.
- **Closing a stream does not cancel the server-side poll.** In local workerd, closing the HTTP stream of a `subscribe` request or a `stream: true` turn does not cancel the Durable Object's event poll over RPC. The poll ends at the turn's next event or when the turn finishes. Behavior on Cloudflare has not been verified.
- **The UI is served from `/`.** A Workers deployment cannot serve TrueForge under a path prefix, so `PUBLIC_BASE_URL` must be an origin without a path.
- **Schedules run at most once per hour.** The minimum interval between runs of a schedule is 3600 seconds.
- **A command shares the turn's 14-minute alarm run.** `SANDBOX_EXEC_TIMEOUT_SECONDS` is capped at two thirds of one alarm run, so a command cannot outlast the pass waiting for it. A skill download is bounded separately at 180 seconds. Combined stdout and stderr from one command are capped at 1 MiB, past which the head is kept and a marker names the full size.
- **A timed-out Code Mode tool call keeps running.** Once Code Mode is available on Workers, the sandbox gets a timeout error when a tool call runs past its limit, but the MCP call itself is not cancelled and may still finish, including a write.
- **A command that a signal kills is reported as a timeout.** Cloudflare Computer maps the usual signal exit codes to "cancelled", so a command the kernel kills, for example for running out of memory, reads the same as one that hit the timeout.
