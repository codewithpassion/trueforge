# PRD: A2A protocol support (Phase 10)

Status: proposed on 2026-09-23. Engineering plan, not user documentation. Intentionally left out of `docs.json` navigation. Nothing in this plan is implemented. Depends on the sibling plan `docs/agent-calling-plan.md` (Phase 9) for the outbound half.

## 1. Problem, goal, non-goals

TrueForge agents are reachable over TrueForge's own REST API, the UI, schedules, and since Cycle 22 the integrations layer (Slack). Every one of those paths assumes a human identity: `withAuth` accepts an OIDC bearer token or the `accessToken` / `id_token` cookies and nothing else (`packages/trueforge/src/auth/token.ts:25-40`, `packages/trueforge/src/app.ts:80-92`), and the OpenAPI description states plainly that there is no user-facing API-key scheme (`packages/trueforge/src/app.ts:154-162`). The Slack plan recorded the consequence as an open gap: an external system has no service credential it can present. The two service bearers that exist, `createApiKeyAuthMiddleware` (`packages/trueforge/src/auth/middleware.ts:33-41`) and the TrueFoundry admin gate (`middleware.ts:48-64`), are deployment-wide and not tenant-scoped or agent-scoped.

Agent-to-agent interoperability is now a standard, not a design question. The Agent2Agent protocol reached **1.0.0** under the Linux Foundation and defines discovery, task lifecycle, streaming, push notifications, and auth. A TrueForge deployment that speaks A2A becomes callable by any conformant client, and can call any conformant agent.

**Goal.** Serve saved TrueForge agents over A2A 1.0, gated by a new admin-issued service credential, and later call remote A2A agents from inside a turn using the same primitives the sibling agent-calling PRD introduces (`call_agent`, per-agent allowlist, shared `trace_id`).

**Direction that ships first: inbound (serving).** It reuses the turn engine, SSE stream, subscribe-with-`Last-Event-ID`, and cancel exactly as they are, it closes the recorded credential gap that also blocks every other machine caller, and it does not depend on the agent-calling PRD landing. Outbound depends on `call_agent` existing, so it follows.

**Non-goals.** gRPC and HTTP+JSON bindings (JSON-RPC only). A2A v0.3 compatibility. Agent registries and federation. Per-caller end-user identity (turns run as the credential's subject, like integrations and schedules). Sandbox artifacts on Workers while sandbox is off there (`docs/cloudflare-workers-port-plan.md` Section 3).

## 2. The protocol as it stands, and the mapping

Read from the v1.0.0 specification at a2a-protocol.org (spec version `1.0.0`, protocol version string `"1.0"`). **v1.0 renamed almost everything the earlier drafts used.** Plans written against v0.3 (`message/send`, `tasks/resubscribe`, lowercase `input-required`, `kind`-tagged parts) are stale.

| Protocol element   | A2A 1.0 as specified                                                                                                                                                                                                                                          | TrueForge mapping                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Discovery          | `/.well-known/agent-card.json`; card carries `supportedInterfaces[]` with per-interface `url`, `protocolBinding`, `protocolVersion: "1.0"`; `capabilities.streaming`, `.pushNotifications`, `.extendedAgentCard`; `skills[]`, `securitySchemes`, `signatures` | One card per saved agent, generated from the agent record and spec                                                                                  |
| Methods (JSON-RPC) | `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask`, `CreateTaskPushNotificationConfig` and siblings, `GetExtendedAgentCard`; header `A2A-Version: 1.0`                                                            | Create session plus turn, poll turn, subscribe, cancel                                                                                              |
| Task states        | `TASK_STATE_SUBMITTED`, `_WORKING`, `_INPUT_REQUIRED`, `_AUTH_REQUIRED`, `_COMPLETED`, `_FAILED`, `_CANCELED`, `_REJECTED` (ProtoJSON enums, camelCase fields)                                                                                                | Turn status union `running` / `done` / `cancelled` / `error` (`packages/trueforge-core/src/agent-session/schemas/turn.ts:110-118`)                  |
| Message and Part   | `Message { messageId, contextId, taskId, role: ROLE_USER/ROLE_AGENT, parts[], metadata, extensions[] }`; `Part` is a oneof of `text` / `raw` / `url` / `data` with `mediaType` (no `kind` discriminator in 1.0)                                               | `TurnInputItem` `user.message` with `UserContentPart` `text` and `file` data-URI parts (`packages/trueforge-core/src/core/events/schema.ts:99-129`) |
| Artifact           | `Artifact { id, parts[], metadata }`                                                                                                                                                                                                                          | Final assistant text, plus produced files from the download route (`packages/trueforge/src/routes/turnRoutes.ts:88-139`)                            |
| Streaming          | SSE; `statusUpdate` and `artifactUpdate` wrappers                                                                                                                                                                                                             | Existing turn SSE (`packages/trueforge/src/apis/turns.ts:421-444`, subscribe `turns.ts:503-529`)                                                    |
| Push               | `TaskPushNotificationConfig { url, token, authentication }`, server POSTs stream responses                                                                                                                                                                    | Claim-first outbox plus `TurnCompletionNotifier` (`packages/trueforge/src/integrations/TurnCompletionNotifier.ts:64-112`)                           |
| Auth               | API key, HTTP bearer, OAuth2, OIDC, mTLS, declared in the card                                                                                                                                                                                                | New `service_credential` bearer, declared as `HTTPAuthSecurityScheme` with scheme `bearer`                                                          |
| Extensions         | Versioned URIs declared on card, message and artifact; `A2A-Extensions` header; `required` flag                                                                                                                                                               | One TrueForge extension for structured `required_actions`                                                                                           |

**Decision: `contextId` is the session id; a task is one turn, or the chain of turns linked by `previous_turn_id` when a turn pauses for input.** The spec defines a context as a grouping of tasks with continuity, which is a TrueForge session, and a task as a unit that reaches a terminal state and cannot restart, which is a turn. The one wrinkle is `INPUT_REQUIRED`: `required_actions` is reported only on a `done` turn (`packages/trueforge-core/src/agent-session/schemas/turn.ts:100-106`) and settling it creates a _new_ turn carrying a `user.tool_approval` or `user.tool_response` item with `previous_turn_id` set, which is what `IntegrationRouter.resume` does (`packages/trueforge/src/integrations/router.ts:224-324`). A2A treats `INPUT_REQUIRED` as interruptible rather than terminal, so `taskId` is the id of the first turn in the chain and an `a2a_task` row tracks the latest turn; `GetTask` and `SubscribeToTask` answer from that latest turn. A message carrying only `contextId` starts a fresh task on that session. A message with neither creates a session and a task. Input items may not be mixed (`turn.ts:161-175`), so a continuation that settles an action must carry the structured reply alone, not a text part beside it.

State mapping: `running` to `TASK_STATE_WORKING`; `done` with empty `required_actions` to `_COMPLETED`; `done` with `required_actions` to `_INPUT_REQUIRED` (`turn.ts:100-106`, action union at `core/events/schema.ts:350-357`); `cancelled` with reason `client-cancelled` or `cancelled-for-next-turn` to `_CANCELED`; `server-execution-timeout` or `abandoned` to `_FAILED` with the reason in the status message (`turn.ts:10-20`); `error` to `_FAILED`; a 422 refusal at turn creation for a known agent to `_REJECTED`. `mcp.auth_required` maps to `_AUTH_REQUIRED`, which no A2A client can settle, so it is terminal for the caller and the status message says to finish the connector authorization in the UI.

## 3. Serving A2A (inbound)

**Endpoints, outside `/api/v1`, mounted without the auth shell in the style of the channel ingress (`packages/trueforge/src/app.ts:378-395`):**

- `POST /a2a/agents/{agent_id}`: the JSON-RPC 2.0 endpoint for one agent.
- `GET /a2a/agents/{agent_id}/card.json`: that agent's card, whose `supportedInterfaces[0]` names the JSON-RPC binding with `url` set to the endpoint above and `protocolVersion: "1.0"`.
- `GET /a2a/agents`: an index of cards the presented credential may reach.
- `GET /.well-known/agent-card.json`: served only when a deployment names a default agent id in config; otherwise 404.

**Path key is the immutable `agent_id`, not the name.** The remote-computers plan made this call for allowlists (`docs/remote-computers-plan.md` Section 5: a name-keyed grant hands access to whoever next creates an agent with that name) and the argument is stronger for a URL an external client hardcodes. The name and description go in the card. Note that session creation today takes a name (`packages/trueforge/src/schemas/session.ts:15-42`), so the A2A handler resolves id to the stored reference itself.

**Auth: `service_credential`.** A2A clients present `Authorization: Bearer tfa2a_<32 random bytes, base64url>`. Stored as sha256 hex with a unique index, never in clear, following `computer.credential_hash` (`packages/trueforge/src/db/computerStore.ts:1-36`). Every request: hash, look up, reject if `revoked_at` is set, check the agent id is in the credential's allowlist, synthesize a `RequestContext` from the credential's tenant and subject through `requestContextFromCreatedBySubject` (`packages/trueforge/src/apis/integrationEvents.ts:125-131`, principal shape at `auth/identity.ts:15-27`), write `last_used_at` best-effort. Every failure is an identical 401, as with `POST /api/v1/computers/enroll`.

**The card requires the credential too, in phase 1.** The deployment is multi-tenant and the agent id is the only routing key, so an unauthenticated card would leak an agent's name, description and skills to anyone holding an id. Agent ids are ULIDs and not guessable, but fail closed is the cheaper default. `capabilities.extendedAgentCard` is false; a per-agent `config.a2a.public_card` can open the base card later.

**Which agents are exposed: both gates must pass.** The agent spec opts in (`config.a2a.exposed`, in `RuntimeConfigSchema`, `packages/trueforge-core/src/agent-session/schemas/agentSpec.ts:215`) and the credential's allowlist names the agent id. A non-exposed agent answers 404 to a credential that lists it, so revoking exposure is one edit.

**Long-running tasks.** `SendStreamingMessage` maps to a `stream: true` turn, which on Workers keeps the Durable Object alive for the whole turn (`docs/cloudflare-workers-port-plan.md` Section 7 records that streaming turns completed even after the HTTP client disconnected, while non-streaming starts needed the holding alarm). `SendMessage` therefore starts the turn streaming internally and drains for a bounded wait, returning `_WORKING` plus the task id when the wait expires rather than holding an HTTP request open. `GetTask` reads the turn poll route's data (`turnRoutes.ts:61-86`). `SubscribeToTask` maps onto subscribe with `Last-Event-ID`, which is an exclusive resume on a per-stream sequence number (`apis/turns.ts:98-114`); the A2A SSE frame id carries that same number. `CancelTask` maps to session cancel (`routes/sessionRoutes.ts:226-263`). Note that TrueForge SSE frames carry no `event:` name (`apis/turns.ts:86-96`), so the A2A layer builds its own frames from the JSON `type` field.

**Artifacts.** The final assistant message becomes one artifact with a `text` part. Produced files become artifacts with a `raw` part when under 1 MiB, otherwise a `url` part pointing at `/a2a/agents/{agent_id}/tasks/{task_id}/artifacts/{artifact_id}`, a thin proxy in front of the existing download route that accepts the same service credential.

**Rate limits and isolation.** Per-credential token bucket on JSON-RPC calls and a concurrent-task cap, both rejected as JSON-RPC errors. Tenant comes only from the credential record, never from the path or body, matching the integrations rule.

## 4. Calling A2A agents (outbound)

A new settings entry type `a2a_agent` sits beside MCP servers: card URL, credential, optional pinned interface. Records mirror `McpServerRecord` (`packages/trueforge/src/db/mcpServerStore.ts:11-20`) with redaction on read (`packages/trueforge/src/utils/secretRedaction.ts:10-15`). Two consumers, one client:

- As a tool source: an `A2AAgentSource implements ToolSource` beside `RemoteMCP` (`packages/trueforge-core/src/core/mcp/RemoteMCP.ts:49`), constructed in the same loop that resolves `spec.mcp_servers` (`packages/trueforge-core/src/agent-session/TurnResourceResolver.ts:166-210`) from a new `spec.a2a_agents[]`. Each card skill becomes one tool.
- As a `call_agent` target: the sibling PRD's per-agent allowlist gains remote entries, so one tool call reaches either a local agent or a remote A2A agent with the same tracing.

All outbound traffic, including card fetches and push webhooks, goes through the SSRF guard (`packages/trueforge-core/src/core/util/ssrfGuard.ts:310-320`). Streaming uses bounded waits, never an unbounded park: `docs/remote-computers-plan.md` Section 11 showed that time parked without a storage access is what gets a Durable Object instance replaced under a running turn. File parts under the inline cap only. `CancelTask` is sent when the calling turn is cancelled. Calling out is a prompt-injection amplifier, so remote targets are admin-configured, per-agent allowlisted, and their output is labelled as untrusted in the tool result.

## 5. Data model and API

- `service_credential`: `id` (ULID), `tenant_id`, `name`, `token_hash` (unique), `subject_id`, `subject_type`, `subject_display_name` (the `CreatedBySubject` shape at `packages/trueforge-core/src/agent-session/schemas/subject.ts:4-12`), `created_by_subject`, `created_at`, `last_used_at`, `revoked_at`.
- `service_credential_agent_access`: `credential_id`, `agent_id`, `agent_name` (display only), primary key on both, keyed by immutable id.
- `a2a_task`: `task_id` (the first turn's id), `tenant_id`, `session_id`, `context_id`, `latest_turn_id`, `credential_id`, `last_message_id` (the `messageId` idempotency guard), `push_url`, `push_token`, `created_at`, `updated_at`. This row is the single owner of the task-to-turn mapping; push deliveries ride an outbox row with the claim-first `pending` to `sending` guard (`packages/trueforge/src/db/sqlite/integration-store/SqliteIntegrationStore.ts:304-327`).
- `a2a_audit`: `id` (ULID), `tenant_id`, `credential_id`, `agent_id`, `method`, `task_id`, `outcome`, `duration_ms`, `created_at`, written from a `finally` and swept on a retention schedule, shaped like `computer_audit`.
- `a2a_agent`: tenant-scoped outbound entry, phase 4 only.

Three paired migrations per table, Postgres plus SQLite plus D1 `.sql`, following `20260921_000002_computer.ts` and `migrations/d1/0005_computer.sql`. On Workers, `packages/trueforge/wrangler.jsonc` needs `run_worker_first` entries for `/a2a/*` and `/.well-known/*`; the channel ingress rides the existing `/api/*` entry and these paths do not, so the static asset layer would answer first.

Session source gains an `a2a` arm `{ type, credential_id, context_id }` in the existing discriminated union (`packages/trueforge-core/src/agent-session/schemas/session.ts:77-107`).

Routes: `GET/POST /api/v1/settings/service-credentials` (create returns the token once), `GET/DELETE .../{id}`, `GET/PUT .../{id}/agents`, `POST .../{id}/revoke`, all admin-only inside the settings router (`packages/trueforge/src/apis/settings.ts`). These are documented in OpenAPI and regenerate the SDK. **The A2A JSON-RPC surface is excluded from OpenAPI**, marked `x-fern-ignore` and `x-excluded` like the channel ingress (`packages/trueforge/src/routes/integrationRoutes.ts:221-255`): it is one POST with a polymorphic body, and forcing it into the REST document would produce a useless SDK and pollute the published spec. The card is documented, since it is a plain GET.

Any catalog or DTO type the new Settings sections need on the UI side is defined in `packages/assistant-ui-runtime/src/server/types.ts` and re-exported as a pass-through alias from `packages/trueforge-ui/src/server/types.ts`, per the server-port rule.

UI: a Settings section for service credentials and one for A2A agents, registered by adding the id to `SettingsSection` (`packages/trueforge-ui/src/server/ShellModeContext.tsx:74`) and the nav entry (`packages/trueforge-ui/src/containers/SettingsBuilder/index.tsx:84-112`), beside `ComputerSettings.tsx`; an "expose over A2A" toggle in the agent config panel bound to `config.a2a.exposed`.

## 6. Tracing

`contextId` is the session id and `taskId` is the id of the task's first turn, both returned verbatim so a caller's logs join TrueForge's; `a2a_task.latest_turn_id` resolves a task to the turn currently answering for it. A `trace_id` rides `Message.metadata` under a namespaced key, `trueforge.dev/trace_id`, in both directions: inbound, an existing value is adopted as the session's trace id, otherwise one is minted; outbound, the caller's trace id is copied into the metadata of every message sent to a remote agent, so a chain of A2A hops shares one id with the local `call_agent` chain from the sibling PRD.

## 7. Security

| Threat                                      | Control                                                                                               | Residual             |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------- |
| Stolen credential                           | sha256 at rest, `tfa2a_` prefix for leak scanners, instant revoke checked per request, `last_used_at` | Medium until revoked |
| Replay                                      | TLS plus a per-request `messageId` idempotency check on task creation                                 | Low                  |
| Card enumeration                            | Card requires the credential in phase 1; identical 401s                                               | Low                  |
| Prompt injection through an inbound message | Same exposure as any user message; approvals still hold the turn                                      | High, documented     |
| Prompt injection driving an outbound call   | Admin-configured targets, per-agent allowlist, SSRF guard, results labelled untrusted                 | Medium               |
| Cross-tenant reach                          | Tenant comes only from the credential record                                                          | Low                  |
| Push webhook as an SSRF primitive           | `ssrfFetch` for every delivery, HTTPS only                                                            | Low                  |

Approvals are the sharp edge: an A2A caller cannot click Approve. Phase 1 surfaces `_INPUT_REQUIRED` with a text status message naming the tool and leaves settlement to the UI or Slack. Phase 3 declares an extension URI, `https://trueforge.dev/a2a/ext/required-actions/v1`, carrying the structured `required_actions` as a `data` part and accepting a `data` part reply that becomes a `user.tool_approval` item. Audit: every JSON-RPC call writes a row with credential id, agent id, method, task id and outcome, retained like `computer_audit`.

## 8. Phases

- [ ] **Phase A1: service credentials.** Table, paired migrations, admin routes, Settings section, audit rows. Acceptance: a credential can be created, listed with the token shown once, scoped to one agent id, revoked; a revoked credential fails closed; OpenAPI and SDK regenerated; changesets added. Live test: create a credential on the deployed Workers build and confirm a revoked token is rejected with an identical 401.
- [ ] **Phase A2: inbound A2A for one exposed agent.** Card, JSON-RPC handler for `SendMessage`, `SendStreamingMessage`, `GetTask`, `CancelTask`, `SubscribeToTask`, state mapping, text parts, final-text artifact, `config.a2a.exposed` toggle. Acceptance: the official `@a2a-js/sdk` client (v1.0, JSON-RPC binding) fetches the card, sends a message, streams to completion, polls, and cancels. Live test: run that client from a laptop against the live Workers deploy for a short turn, a 3-minute turn, and a cancel.
- [ ] **Phase A3: input-required, artifacts, push.** The extension for `required_actions`, resume by `taskId`, file parts in and artifacts out, `CreateTaskPushNotificationConfig` on the outbox. Acceptance: a turn that needs an approval reaches `_INPUT_REQUIRED` and is settled by a follow-up message; a produced file arrives as an artifact; a webhook receives the terminal status. Live test: same client, approval-gated agent, webhook on a public endpoint.
- [ ] **Phase A4: outbound.** Settings entry, `A2AAgentSource`, `call_agent` remote targets, trace propagation. Acceptance: a TrueForge agent calls a reference A2A server and the trace id appears on both sides. Live test: one TrueForge deployment calls another over A2A.

Each phase runs as a forge agent in a worktree, gets an Opus review, records a cycle in `PROGRESS.md`, lands fast-forward on `dom/main`, deploys, and the controller runs the live test.

## 9. Decisions and open questions

1. **Pin A2A 1.0.0, JSON-RPC binding only, no v0.3 compatibility interface.** The 1.0 rename touched method names, enum encoding and the `Part` shape; supporting both doubles the surface for peers that are themselves migrating.
2. **A task is a turn chain, a context is a session**, rather than one task per session. A session is not terminal and a task is, and the chain exists only because settling a required action starts a follow-up turn.
3. **Card behind the credential** in phase 1. The phase A2 live test therefore configures `@a2a-js/sdk` with a `fetch` override that adds the bearer header, since its card resolver must send the credential; if that override turns out not to reach the card fetch, the fallback is to set `config.a2a.public_card` on the test agent rather than to weaken the default.
4. **A2A routes excluded from OpenAPI**, settings routes included.
5. **Spec churn.** 1.0 is stable but extensions and bindings will move. The card is generated from one module, so a version bump is a card change plus a codec change; the phase A2 acceptance test is the regression guard.
6. Open: whether `ListTasks` is worth implementing (recommend yes in A3, it maps to the turn list route and reference clients call it).
7. Open: whether inbound A2A should reuse `ChannelAdapter` (`packages/trueforge/src/integrations/types.ts:109-132`). Recommend no. That port assumes a signed webhook and an outbox reply, while A2A is a synchronous JSON-RPC surface with its own auth; reuse would bend both. It should reuse the outbox and `TurnCompletionNotifier` for push only.
8. Open: multi-tenant card hosting at the origin root. Recommend the path-based card plus direct client configuration, and a root card only for single-agent deployments.
