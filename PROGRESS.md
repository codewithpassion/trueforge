## Cycle 39 — Phase 9a-2: images in tool results, plus integration with 9b (2026-09-24)

**Goal:** Ship phase 9a-2 of `docs/remote-desktop-plan.md` (§5.2) so tools can return images, and wire the 9b `computer_*` tools to return real screenshots.

**What we did:**

- **Content model.** Tool message content is now always `ToolContentPart[]` (`text` | `image {file_id, media_type, width, height}`). `normalizeToolContent` runs at every read boundary: the Postgres/SQLite/D1/InMemory stores, context replay, sub-agent completions, Redis live replay, and the Workers `turnEventWire` decode. The harness owns `LLMRequestMessage` at the ILLM boundary.
- **Write path.** `executeToolCalls` sniffs the header (PNG/JPEG/GIF/WebP, dimensions read from the header, `image/jpg` treated as jpeg) and stores the image in the session file store. Limits: 3.75 MiB per image, at most 8000 px per side.
- **Providers.** `VercelAILLM` emits ai@7 `{type:'content', value:[text, file]}` for anthropic, openai Responses and google. openai-compatible, moonshot and alibaba get a text stub. When more than 2N images are live, the oldest are stubbed down to N (N=5) in one batch, which keeps the Anthropic cache prefix stable. Each request has a 20 MiB base64 budget, images are cached per turn, and they count toward the context estimate.
- **Computer tools.** They return real screenshots through `toolImageResultResponse`. The desktop instructions warn when the provider can't take images.
- **SDK.** Regenerated with a major changeset: `tool.response` content is a list of parts. It also adds `sandbox.desktop`, the `desktop` capability, and audit op `desktop`.
- **Reviews.** 0 blockers, 3 majors, all fixed: no chat thumbnails (deliberately deferred to the 9c UI step), one bad image could brick a session, and the server wiring had no end-to-end test. The re-review of the fixes plus the 9b integration found two more wedge paths, no pixel cap and no per-request byte cap. Both fixed in `83bdf790`.
- **Shipped.** Landed on `dom/main` at `83bdf790` and deployed as Workers version `27227fd1` (no migration).

**Lessons learned:**

- Anything replayed on every request, like images in history, needs every provider limit enforced at write time. Otherwise one bad item wedges the session for good.
- The first review fixed the per-image size and missed pixel dimensions and total request bytes. Every provider limit needs its own check.
- The 9b note that the UI drops `sandbox.desktop` on save was wrong: the SDK passes unknown keys through. Carried-over claims like that should be checked with a test before anyone plans work around them.

**Avoid next time:**

- Don't add a replayed input type without listing each provider limit (bytes, pixels, count, per-request total) and checking all of them at write time.
- Don't let an image lookup failure fail the turn. Fall back to the stub.
- Don't repeat a "known bug" from an earlier cycle without reproducing it.
- Next: 9c server merge (takeover flow and desktop routes, in progress), SDK regen, then the 9c UI (Screen page/panel, settings Desktop tab, takeover card, computer tool cards and thumbnails), then a live browser test.

## Cycle 38 — Phase 9b: desktop on the daemon, agent computer tools, agent lease (2026-09-24)

**Goal:** Ship phase 9b of `docs/remote-desktop-plan.md`: the daemon runs a desktop, and agents drive it through `computer_*` tools while holding a turn-scoped lease.

**What we did:**

- **Daemon (`e761e595..cc244a58`).** `--desktop` supervises Xvfb (with an `-auth` cookie, `-nolisten tcp` and `-nolisten local`) plus openbox. X capture is pure Go via `xgb`, so CGO stays off. Input and clipboard go through `xdotool`/`xclip`, and `DISPLAY`/`XAUTHORITY` are added to the scrubbed exec env. Each op type has a budget semaphore. Keys must match a regex and xdotool command names are rejected. Scroll is capped at 60 clicks per batch.
- **Packaging.** `Dockerfile.desktop` is Debian-based. A chromium wrapper clears stale Singleton locks left by other container hostnames, and the password manager is off. The Chromium sandbox works in Docker with only `--security-opt seccomp=packages/trueforge-computer/packaging/desktop/seccomp.json`, which is the default profile plus `clone`/`unshare`. `install.sh --desktop` supports Debian only and refuses snap chromium.
- **Server (`0a8ca397..5a8322e5`).** The protocol gains desktop ops and `capabilities.desktop`. `RemoteComputerDO` keeps a lease with a principal. The agent lease is keyed by `{session_id, turn_id}` and released by a composable `onTurnDrained` hook, which now covers the Node streaming path too. Human lease methods exist, but their routes wait for 9c. While a human holds the lease, every agent op except `cancel` is refused.
- **Clipboard clearing.** `read_only` and `desktop_unavailable` both count as cleared. After 3 failed clears, non-desktop ops resume.
- **Tools.** `computer_*` tools return a text stub where images belong until 9a-2 lands. `require_approval` offers only screenshot and clipboard read. Audit rows use op `desktop`.
- **Reviews.** Daemon: 0 blockers, 3 majors. Server: 0 blockers, 7 majors. The re-review on the merged branch found a typecheck blocker introduced by the merge and a bug where clipboard clearing could wedge forever. Both fixed in `55b16535`.
- **Shipped.** Landed on `dom/main` at `55b16535` and deployed as Workers version `113696e7` (no migration).

**Lessons learned:**

- vitest doesn't typecheck. Both branches passed their tests, and the merge still broke `pnpm typecheck`.
- Per-branch reviews missed bugs that only show up once the daemon and server branches are merged. The re-review on the integration branch found the typecheck blocker and the clearing wedge.
- A relay that folds every reply error into `bad_request` hides error codes the caller needs.
- Any "retry until cleared" state needs an exit. Without the 3-failure cutoff, one broken clipboard blocked every later op.

**Avoid next time:**

- Don't land an integration merge without running `pnpm typecheck` on it.
- Don't treat per-branch review approval as approval of the merged result. Re-review the integration branch.
- Don't collapse distinct daemon error codes at a relay boundary.
- Still open: SDK regen for `sandbox.desktop` (the UI drops it on save until then; bundled with 9a-2), chat thumbnails, and 9c.

## Cycle 37 — Phase 9a-1: session file store (2026-09-24)

**Goal:** Build the session file store from `docs/remote-desktop-plan.md` (phase 9a-1), so later phases can persist screenshots and other binary session artifacts.

**What we did:**

- **Store (`ee481e40`).** `IFileStore` / `SessionFileStore` live in `packages/trueforge-core/src/agent-session/store`. Three backends: R2 (binding `FILES`, bucket `trueforge-rockyshoreslabs-files`), S3 through `aws4fetch`, and a filesystem default (`FILE_STORE_DIR=/data/files` in the Dockerfiles, owned by uid 10001). Metadata goes in a new `session_file` table on D1, Postgres and SQLite (D1 migration `0009_session_file`). The S3 backend has only been tested against a fake, never a real bucket.
- **Route and limits.** `GET /api/v1/sessions/{session_id}/files/{file_id}` checks access with `canReadAgentBoundResource` and returns 404 when access is denied. Responses carry a CSP `sandbox` header and `nosniff`. Writes accept only `image/(png|jpeg|webp|gif)`.
- **Deletion.** The session-delete route removes files in three steps: sweep files, delete the session, sweep again, so a file written during the delete is not left behind.
- **Helm.** New `fileStore` values. The filesystem backend refuses to start with more than one replica or with autoscaling on, so the medium and large tiers will not start until S3 is configured.
- **Adversarial review.** 0 blockers, 2 majors: the default directory in the container was not writable, and file authz did not match the rule used for turns. Both fixed (`9de205b2`, `0692d4bf`) and the re-review said LAND. `62f1e48c` then removed an unreachable 404 check in S3 DeleteObjects.
- **Shipped.** Landed on `dom/main` at `62f1e48c` and deployed as Workers version `137009b1` with D1 `0009_session_file` applied. Still in flight: 9b daemon and server fix rounds, and 9a-2 (image tool results).

**Lessons learned:**

- `wrangler d1 migrations apply` can print error 7403 after it has already applied the migration. Query `d1_migrations` before retrying.
- `(cmd | tail) && next` takes the exit code from `tail`, not `cmd`, so the deploy ran even though the migration step had failed.
- Worktrees created by the Agent tool started from `origin/main`, not `dom/main`, so a forge agent can build on the wrong base without noticing.
- A filesystem default that works on a dev host can still fail in the container: the image runs as uid 10001 and the default directory was not writable. The review caught this; the tests did not.

**Avoid next time:**

- Don't pipe a deploy or migration step through `tail`/`head` inside an `&&` chain. Use `set -o pipefail` or check the step's own exit code.
- Don't retry a D1 migration after an error without checking `d1_migrations` first.
- Don't start a forge worktree without checking its base commit against `dom/main`.
- Don't give a new resource route its own authz rule. Reuse the one that guards the sibling resource (turns).

## Cycle 36 — Agent description made optional (2026-09-23)

**Goal:** Make the agent description optional, as the user asked ("make it not mandatory unless that would mean a db change"). No DB change was needed: the column is already `TEXT NOT NULL DEFAULT ''`.

**What we did:**

- **Feature (`02b17493`) and SDK regen (`2e0312cc`).** API: creating an agent without a description stores `''`, sending `''` on update clears it, leaving it out on update keeps the old value, and the 1024-character limit stays. OpenAPI and the SDKs were regenerated in their own commit.
- **UI.** The field is labelled "Description (optional)" and Save works without it. Leaving it blank on Update Agent clears it. Save and clone share one helper, `agentDescriptionField.ts` (`b8cd10ec`).
- **Fable review, first fix round (`cdcc9ba1`).** No blockers, but two bugs. Clearing the description in Update Agent did nothing, because the UI compared against stale shell state instead of the server value. Import still copied the name into the description; it now stores `''`.
- **Re-review, second fix round (`6f7327a8`).** Found that `clearChat` dropped the description. Fixed that. Also, older rows where the description equals the name now show a blank description in the list row and on Edit.
- **Verification.** The reviewer ran the Postgres store tests on a throwaway container (256 pass). A Sonnet agent drove agent-browser (headless Chrome) against a local standalone build and passed 7/7 checks. Landed on `dom/main` at `6f7327a8` and deployed as Workers version `eeffec00`.
- **Not fixed:** cloning from the library still pre-fills the description with the name on older agents where the two match. We chose to leave it.

**Lessons learned:**

- For a "make it optional" change, three cases need separate handling: field omitted, field sent empty, and field sent with a value. The first version got the API right but the UI never sent `''`, so a cleared field looked unchanged and nothing was written.

- Old data still carries the previous rule (description set to the name), so every place that displays or copies it (row, Edit, import, clone) has to be checked, not only the form.
- The fix to how descriptions are saved introduced a new bug in `clearChat`, and only the re-review caught it. Re-reviewing after the fix round paid off again.

**Avoid next time:**

- Don't use client shell state to decide whether a field changed; compare against the server value, or send the field explicitly.
- Don't stop at the form when relaxing a required field. Grep every path that creates or copies the entity (import, clone, clear/reset) for the old default.
- Don't skip the re-review after a fix round that changes how shared state is rebuilt.

## Cycle 32 — Phase 8b live test: the turn died on the caller, not on the relay (2026-09-22)

**Goal:** Fix what the live test of remote computers found twice on version `418acfec`: a turn whose remote `exec` ran about 45 s ended `cancelled` with reason `client-cancelled`, and so did a turn whose exec output was 2 MB. Short commands with small output never failed.

**What we did:**

- **Followed the stack instead of the story.** The brief read as "a long DO-to-DO RPC cannot be held", and the relay looked guilty. The tail said otherwise: `RemoteComputerDO.request` ran 45,019 ms and returned `ok`, and the `SessionDO` alarm holding the turn died 218 ms **after** that. Both stacks name `SessionDO`'s own storage — the drain in `DurableObjectEventSubscription.put`, then the alarm's `finally` in `deleteExpired` — with `Connection closed: this Durable Object instance is no longer active.` Reading the code closed it: `RemoteComputerProvider` catches every relay rejection and turns it into an `interrupted` outcome, so a failing relay can never surface as a drain error at all.
- **Named the root cause: a superseded instance keeps running.** The platform restarts or moves a Durable Object for its own reasons, and it tells the replaced instance nothing. An invocation parked on an outbound RPC needs no claim on the object, so it runs on and only finds out at its next storage access. The exposure is time parked without touching storage, which is why a 45 s command and a 2 MB payload failed the same way and a 2 s command never did. No deploy was in flight for either sighting.
- **Contained the zombie rather than redesigning the relay.** `RemoteComputerDO` and the frozen v1 wire contract are untouched. The holding alarm now probes its own storage every five seconds while it waits; when the probe fails it cancels the turns it holds with `Abandoned`, skips the storage work in its `finally`, and ends the pass without an exception so the invocation's outcome stops blaming the code.
- **Closed the Cycle 13 backlog item on the way.** A turn ended by a lost instance is recorded `abandoned`, not `client-cancelled`. It is the same cancel path `SessionDO.cancel` already uses, so Node behaviour is unchanged: none of this code runs there.
- **Stopped one alarm invocation holding another's turns.** `alarm()` arms a 60-second fallback on entry and then holds for up to 14 minutes, so every turn over a minute gets a second invocation that would park on the same promises and hold the object twice. It now pushes the fallback out and returns. Each pass logs an instance id, because the platform names no instance and the live tail could not say which one ran what.
- **Reproduced what could be reproduced.** Workerd never supersedes an instance, so the probe is a one-function module a test replaces to make it fail the way a moved-away object's storage does. The 2 MB round trip is real end to end: through the relay and the RPC at provider level, and through a whole turn, where it takes over 30 s locally — the same slowness that left the live turn's alarm parked for 21.6 s. A held command answered past the 25-second staleness threshold guards the other half of the claim: the relay waits out a slow machine rather than declaring it gone. The three tests add about 33 s to the workers suite.

**Lessons learned:**

- A symptom that correlates with a feature is not evidence the feature is at fault. Long commands and big payloads both correlate with "the caller sits still for a long time", and that was the actual variable.
- Read the error's catch sites before believing where it came from. One `try/catch` in the provider ruled out the entire relay before any test was written.
- An invocation that parks for tens of seconds is making a bet that its instance survives. On Durable Objects the loser of that bet is told nothing, so anything holding a turn has to ask.
- `client-cancelled` is what a broken event iterator looks like from inside the agent loop. Any cause that breaks the drain wears that label until something upstream gives the turn a better reason.

**Avoid next time:**

- Don't take a reported root cause as the starting point when the tail is available; the brief's chain and the stack disagreed at the first link.
- Don't arm a fallback alarm for a fixed delay and then hold the invocation for much longer than that, unless a second invocation arriving mid-hold is harmless.
- Don't reach for a store-and-poll protocol redesign to fix a symptom the evidence puts on the other side of the RPC.

## Cycle 31 — Upstream merge: 74 commits, 35 conflicts, and a patch that deleted itself (2026-09-22)

**Goal:** Merge upstream `origin/main` into the fork without losing the Workers port, remote computers, Slack, or Code Mode.

**What upstream brought:** Web search (`agent_web_search` migration, a provider port on the turn resolver, a `web_search` capability), `active_executor_id` on turns, an outbound URL guard (SSRF) with `NETWORK_POLICY_ENABLED` and host allow/block lists, an mTLS env rename (`TRUEFORGE_MTLS_*` → `MTLS_*`), Postgres TLS and schema config, a per-tenant model-provider allowlist, inline MCP and skill resolution from `x-tfg-*` headers, session rename, agent clone, MCP approval in the builder, and a release to 0.2.0 out of pre mode.

**What we did:**

- **Merged the real tip, not the briefed one.** The task was scoped against `e5e651cd` (58 commits, 18 conflicts). `origin/main` had moved to `0da3794d` — 74 commits, 35 conflicts. `e5e651cd` is an ancestor, so nothing was lost by merging the tip directly, and staging through it would only have meant doing the runtime work twice.
- **The patch deleted itself.** Upstream #826 moved `@truefoundry/assistant-ui-runtime` into the monorepo as `packages/assistant-ui-runtime`, renamed it `@truefoundry/trueforge-assistant-ui-runtime` (`workspace:*`), and dropped `patchedDependencies` from `pnpm-workspace.yaml` entirely. The briefed job — re-roll our 0.1.37 patch against 0.1.43 — had no npm dependency left to patch. The three additions (`integrationCatalog`, `computerCatalog`, `AgentSandboxConfig.computerId`) become ordinary source edits in a package we now own in-tree. Checked first: the in-repo runtime does not already expose the slots, so the port is still needed.
- **Deep imports stayed deep.** Upstream consolidated `@truefoundry/trueforge-core/core/...` imports onto the barrel. Our Workers code imports deep paths exclusively and never the barrel, so every import-block conflict was resolved to deep paths plus upstream's new symbol. `winston` `Logger` in `TFYSandboxProvider` stayed on our own logger module for the same reason.
- **Five files kept our shape.** `config.ts`, `main.ts`, `apis/turns.ts`, `apis/sessions.ts`, `apis/schedules.ts` are seams the Workers port owns: a three-runtime discriminated union instead of upstream's standalone boolean, turn execution behind `TurnExecutor`, cancel in `runtime/nodeTurnExecutor.ts`. Upstream restructured the same code. Taking their side would have deleted the port; taking ours defers their behaviour. We took ours and wrote the deferred list down rather than pretending the merge was complete.

**Lessons learned:**

- Verify the merge base before planning the merge. The briefing's tip, commit count and conflict count were all stale, and the 16 commits nobody mentioned contained the one change that invalidated a whole numbered step.
- A conflict list is a scope estimate, not a work estimate. Thirty of 35 files were mechanical unions; the remaining five were two teams restructuring the same file in different directions, and those five are most of the real work.
- When upstream absorbs a dependency you were patching, the patch is not migrated — it is deleted and its content re-homed. Check what the dependency _became_ before re-rolling anything against it.
- Resolving a file to "ours" is a decision to port behaviour later, not a resolution. It has to be recorded as such or it silently becomes a regression.

## Cycle 30 — Phase 8b live test: one missing Python package stopped every command (2026-09-22)

**Goal:** Fix what the next live test of remote computers found. A machine with `python3` and `git` but without the `pydantic` package connected fine, and an agent with **no skills** then failed every `exec` with `Sandbox initialization failed: (exit code 1): Traceback ... skill_downloader.py, line 89 ... from pydantic import ...`.

**What we did:**

- **Named the real cause: an optional feature took the basic one down with it.** Sandbox init always attaches a `SkillMounter` — deliberately, since 7b, so a skill the agent dropped is cleaned up on the next init — and its init exec runs the downloader whether or not there is anything to download. On a remote computer the server gated skills on `hello.capabilities` `{ python3, git }`, which is not what the downloader needs: it imports `pydantic`. Two tools present, one package missing, and a machine that could run nothing at all.
- **The client answers the question instead of the server guessing at it.** `hello.capabilities` gained `skills`, computed by the client: `python3` and `git` on `PATH` **and** `python3 -c "import pydantic"` exiting zero, run as argv under a 10 s timeout. `protocol_version` stays 1 — the field defaults to false, so a client and a stored row from before it still parse, and false is the safe direction. The canonical owner is `packages/trueforge/src/computers/protocol.ts`; the Go `internal/protocol`, `internal/state`, `trueforge-computer status`, `docs/remote-computers-protocol.md` and the golden fixture follow it, and the server test that parses that fixture holds both sides to the same bytes.
- **No mounter at all when the machine cannot run one.** The Workers integration picks the mounter per turn: a `RemoteComputerProvider` whose machine reports `skills: false` gets `undefined`, so sandbox init uploads nothing and runs no downloader, and a plain `exec` works. Every other provider is untouched — the built-in workspace, Daytona, TFY, local and Node still mount unconditionally, which is what keeps skill cleanup working there.
- **An agent that does ask for a skill is refused, in words.** `resolveSandboxUsability` now takes `skills_requested`, and `resolveComputerUsability` answers the new reason `computer_no_skills` when the stored row says the machine cannot mount them. One message, owned by `computerNotUsableMessage`: `cannot mount skills: it needs python3, git and the pydantic package`. It comes out of spec validation, out of the turn's allowlist re-check, and out of the turn's own check against the live hello — the last one matters because a machine can lose pydantic between saving an agent and running it. A computer that has never connected reports `null` capabilities and is not refused at validation: there is nothing to refuse it on yet.

**Lessons learned:**

- A capability gate must test what the feature actually needs, not what someone remembered it needing. `python3` and `git` were the two visible tools; the third requirement lived on line 89 of a script nobody was reading.
- An optional feature must not be able to break the basic one. Skill mounting is an extra on a remote computer; the cost of it failing should have been "no skills", not "no commands".
- The machine is the only thing that can answer "can I import this". A boolean the server derives from two `LookPath` results is a guess wearing a capability's clothes — which the plan's own "for protocol v2" note had already said, and which was cheaper to do additively than it looked.
- A defaulted field is an additive wire change. It is also the only kind that survives rows already in the database: `Schema.parse(row)` runs over every stored capability document.

**Avoid next time:**

- Don't gate a feature on the tools its implementation happens to shell out to. Gate it on the implementation succeeding, and let the side that can run it say so.
- Don't let an "always run it so cleanup happens" step be unconditional across providers that do not all have the same runtime.
- Don't add a required field to a schema that parses persisted documents. Check where the schema is used before deciding it is only a wire shape.

## Cycle 29 — Phase 8b live test: the server stops guessing where a machine keeps its sessions (2026-09-22)

**Goal:** Fix what a live test of remote computers found. Enroll, connect, online status and grants all worked; every `exec` came back `Sandbox initialization failed: (exit code 127): fork/exec /bin/sh: no such file or directory`, on a machine where `/bin/sh` exists.

**What we did:**

- **Found two causes and one lie.** The client ran in its own container image — busybox, uid 1000, read-only rootfs, sessions under `/var/lib/trueforge-computer/sessions`, `HOME=/tmp`. The server had derived the session directory from `run_as_user` and `os`, so it sent `mkdir -p '/home/trueforge/.trueforge/sessions/<id>/uploads'` with `cwd` set to `/home/trueforge/.trueforge/sessions/<id>` — a directory that existed nowhere on that machine. Go reports a missing `cmd.Dir` as `fork/exec /bin/sh: no such file or directory`, which is why everyone read it as a missing shell. And the client's audit log recorded `outcome: ok` for it, because the runner only returned an error when it refused the work, never when the process failed to start.
- **`hello` gained a required `workdir`.** Still `protocol_version: 1`: no client had shipped, so there was nothing to keep compatible and a compatibility shim would have been a shim for nobody. The canonical owner is `packages/trueforge/src/computers/protocol.ts`; the Go `internal/protocol`, `docs/remote-computers-protocol.md` and the golden fixtures under `packages/trueforge-computer/testdata/protocol/` follow it, and the server test that enumerates that directory still holds both sides to the same bytes. It is a hostile string, so the schema bounds it: at most 1024 characters, leading `/`, at least one segment, no `.`/`..` segment, no trailing slash, and none of NUL, a control character, `'`, `"`, a backtick, `\` or `$`. Un-normalised would have been the quiet failure — `/x/sessions/` stops matching the download jail's normalised comparison and refuses every transfer.
- **The client settles the working directory before it starts anything.** `Policy.ResolveExecDir` sits where `within` and `resolveExisting` already live: a null `cwd` means the workdir; a directory under the workdir that is missing is created with `MkdirAll` at `0700`, symlinks resolved first so a link inside it cannot build a tree outside; anything else must exist and be a directory, or the exec is refused `bad_request` with `working directory does not exist: <path>`. `hello.workdir` and `runner.DefaultCwd` are now the same resolved value, not the raw flag in one place and the resolved one in the other.
- **The client's audit tells the truth.** `Runner.Run` returns a `Completion` carrying `Started` and a reason, rather than only the wire `ExecResult`, so the agent records `ok` only for a command that ran. A start failure and both cancelled-before-start paths are `error` with the reason. `ExecResult` is the wire shape and was left alone.
- **The server reads the path instead of inventing one.** `computerHomeDirectory` and `computerStateRoot` are gone with their tests; `computerSessionDirectory` takes `{ workdir, sessionId }`. The provider holds `workdir: string | null`, and a null one answers offline and sends nothing — the path getters return a named placeholder that no op is ever built from. The init `mkdir -p` is still sent with `cwd: null`, which is now written down as a rule rather than left as an accident.
- **Two holes a passing test would not have found.** The DO read its stored `hello` as `storage.get<HelloMessage>` with no validation, so a hello written by the previous build would have come back typed and short a `workdir`; it is `safeParse`d now. And an unreadable `hello` used to be ignored with the socket left open — a machine the server cannot understand would have gone on taking commands built from a path chosen here — so it is closed with the new code 4400.

**Lessons learned:**

- A server must not guess paths on a machine it does not own. Every derivation from `run_as_user`, `os` or a home directory is a guess that holds only for the machines that happen to look like the one it was written against; the container image we ship ourselves was not one of them.
- An init command cannot use as its `cwd` the directory it is about to create.
- Go reports a missing `cmd.Dir` as `fork/exec <shell>: no such file or directory`. The error names the shell and means the directory.
- An audit log that records `ok` for work that never happened is worse than no audit log: the live test's own evidence pointed away from the bug.
- An unnormalised absolute path passes "starts with `/`" and still breaks a lexical containment check. Bound the shape, not just the characters.

**Avoid next time:**

- Don't add a field to a stored-and-typed shape without re-parsing what storage hands back. `storage.get<T>` is an assertion, not a check.
- Don't leave a frame the server cannot read on an open socket when the unreadable part is what every later message depends on.
- Don't take "the wire result says exit 127" as the outcome. Ask the layer that started the process whether it started.

## Cycle 27 — Phase 8b client: the `trueforge-computer` binary (2026-09-21)

**Goal:** Build the client half of Phase 8b of `docs/remote-computers-plan.md` — a real Go daemon under `packages/trueforge-computer`, against a wire contract frozen in advance so the server half could be written in parallel without either side guessing. Cycle 26 is the server half, written by another agent in its own worktree; this entry covers only the client and the repository wiring for it.

**What we did:**

- **Froze the contract first, and committed it as bytes.** `internal/protocol` is the spike's protocol minus the `probe` op and plus `protocol_version: 1` on `hello`, and `testdata/protocol` holds eleven golden frames — every request the relay sends, every reply the client returns, plus the enrollment pair under `testdata/enroll`. The round-trip test decodes each fixture, re-encodes it, and compares meaning rather than bytes, so the repository's formatter owns the files and the server's Zod schemas can be checked against the same ones later. A `null` `cwd` has its own fixture and its own test, because collapsing it to `""` would silently move a command into the daemon's own directory.
- **Exec is the spike's, with the gaps closed.** `sh -c` under `Setsid`, 124 at the deadline, 128+signal when signalled, `WaitDelay` so a grandchild that escaped the group and still holds the pipes cannot hang the call. Output keeps a **head and a tail** inside one 1 MiB budget across both streams — the spike kept the head only, and 3 MB of build output came back as the first 512 KiB with the failure missing. Both seams are cut back to rune boundaries, bounded to three bytes so binary output keeps its bytes. Four concurrent execs with a 32-deep queue, and a cancel registered before the slot is acquired so it reaches a command that is still waiting.
- **Killing the daemon no longer orphans its commands.** One record per live process group under `<state_dir>/running/`, carrying the group leader's `/proc` start tick on Linux so a recycled pid is not killed by mistake, swept at the next start and again on shutdown. macOS has no portable equivalent and falls back to existence only; the README and the plan both say so.
- **Section 6 is enforced here, not requested.** Deny beats allow, `--read-only` refuses exec and every write while still serving reads, `--workdir-only` compares paths resolved through symlinks so a symlink planted inside the directory is not a way out, the command environment is built rather than inherited so the credential cannot be read back out of it, and every op lands in a `0600` JSON-lines log whose entry shape has no field an environment value could hide in.
- **The reconnect policy is a pure function with an injected clock**, so the close codes are tested in milliseconds against an in-process `httptest` relay: 4401 exits 3 having dialled exactly once, 4409 waits at least five minutes, 4408 reconnects promptly with a growing backoff, and a 401 on the upgrade takes the slow path too. The step resets only after a connection that lasted, which is the bug that let two clients with one credential evict each other forever.
- **A reply whose socket has closed is dropped**, never written to the next one. The exec registry, by contrast, is global, so a `cancel` arriving after a reconnect still kills a command the previous socket started. The cost is that every op is at-least-once once the relay reissues, which the README states rather than hides.
- **`run --url --code` enrols itself only when it has no credential.** Section 3's `docker run` command re-passes a single-use code on every restart; without this the container works once and then fails forever. The image's entrypoint is `trueforge-computer run`, so the copied command is just the two flags.
- **Packaging:** four static targets from one script, named `trueforge-computer_<os>_<arch>` to match the server's `/install.sh`, with a `SHA256SUMS` beside them — 6,291,608 / 6,095,000 / 6,463,568 / 6,184,098 bytes for linux_amd64, linux_arm64, darwin_amd64, darwin_arm64, all under the 10 MB Section 7 budgeted and in line with the spike's 5.8 MB. A busybox image (a shell is needed for `sh -c`) carrying a CA bundle, running as uid 1000, verified under `--read-only --tmpfs /tmp --cap-drop ALL`. A systemd unit with `KillMode=control-group`; `install-service` is Phase 8d and exits 4 saying so.
- **Wiring per AGENTS.md:** a `trueforge-computer` path filter with the four shared roots, the matrix id, and root `test:trueforge-computer` (vet, `gofmt -l`, `go test ./...`) plus `build:trueforge-computer`. `actions/setup-go` is conditional on that matrix entry, reading `go-version-file` from the module. It is deliberately **not** in the aggregate `test` script, which the Windows job runs with neither Go nor Docker. No changeset: nothing here is a published npm package.
- **A security review round found three more blockers and nine smaller items.** (1) **A reconnect killed every running command:** the per-session context bounded the work, so a 4408, a laptop waking or a relay deploy SIGKILLed every in-flight exec — the exact opposite of the guarantee Section 10 change 11 makes. Commands now run on the daemon's context and the socket is only the reply sink; a cancel on the new socket still reaches them. (2) **The server could defeat its own allow list through `env`:** with `--allow '^git '`, a `GIT_SSH_COMMAND` or a `PATH` runs anything, and `LD_PRELOAD` does not even need a command. Variables that name a program are refused whenever the operator has constrained the computer, `LD_*`/`DYLD_*` always, with `--allow-env` as the escape hatch — and the whole request is refused rather than the variable quietly dropped. (3) **`http://` sent the enrollment code and the credential in clear**; plaintext is now refused for anything but loopback, and the enrollment call refuses redirects, because a 307 re-sends the body.
- **The rest of that round.** Uploads land in a temporary file and are renamed into place only after the digest agrees, so a failed transfer can no longer truncate or delete the file it was replacing and a symlink swapped in mid-transfer is caught by a re-check at commit time. The state directory is unreachable in every mode except through `sessions/` — `file_put config.json` would otherwise point the next start at an attacker's server, and `file_put running/<n>.json` would make the next sweep SIGKILL a chosen process group. Only regular files are read or written, opened `O_NONBLOCK`, so `/dev/zero` no longer spins the hasher forever. Inbound frames run on a bounded worker pool answering `queue_full` past it, open transfers and file sizes are capped, and `--max-exec-seconds` caps what the relay may ask for. The sweep never kills on existence alone any more: darwin reads the start time through `kern.proc.pid`, and anything that cannot be positively identified is logged and dropped, because a pid is recycled within hours — but **not** by also comparing argv, which the review asked for and which would have been a regression, since dash and bash replace themselves with a lone command and `sh -c 'sleep 400'` becomes `sleep 400` under the same pid and start tick. Allow patterns are anchored to the whole command and deny patterns are tried per line, with the README rewritten to say plainly that these are a speed bump and the run-as user is the boundary.
- **Two corrections came back from the server half, both about promises this README was making on its behalf.** "The server cancels the old id on the next socket" holds for a dropped socket, a stale close, a replacement, a revoke and a rotate — but not after a relay reset, where the object dies with its pending map and the command runs to its own `timeout_ms`. And the server's confinement of file paths to the session directory is lexical, so a symlink inside that directory is invisible to it: the client's symlink resolution is what protects the state directory unconditionally, and `--workdir-only` is the only thing that confines anything else. Both are now in the README where an operator reads them, rather than as a guarantee nobody keeps.
- **A re-review then replaced the environment denylist with an allowlist, which is the substantive change of the third round.** The denylist was whack-a-mole and losing: past `PATH` and `GIT_SSH_COMMAND` sit `HOME` with an uploaded `.gitconfig`, `XDG_CONFIG_HOME`, `KUBECONFIG` exec plugins, `AWS_CONFIG_FILE` `credential_process`, `BASH_FUNC_*`, `RUSTC_WRAPPER`, `CC`, `SSL_CERT_FILE` — and each one found is evidence of the ones not found. It also refused things core legitimately sets. So: once any policy flag is set the environment is an allowlist of a small safe set plus what `--allow-env` names, with a trailing `*` for a family; with no policy, everything but `LD_*`/`DYLD_*` passes. The README says plainly that granting `GIT_CONFIG_*`, which skills need, is equivalent to allowing arbitrary commands, and that a `cwd` pointing at an uploaded repository with `core.fsmonitor` defeats `--allow '^git status$'` with no environment at all. The same round: path containment now compares device and inode rather than strings, because `filepath.Rel` is case-sensitive and APFS is not, so `~/.TRUEFORGE/credential` would have escaped the state-dir refusal on macOS; a `--workdir` overlapping the state directory is refused at startup; a duplicate request id gets its own `duplicate_id` code so the server reads it as "still running"; an upload carries over the destination's permission bits; `*.localhost` no longer counts as loopback; and every `Run` in the connection tests goes through a bounded helper, so a misclassified close code fails instead of hanging for the test timeout.
- **An earlier adversarial review round found two blockers, both from the same blind spot: every test drove one request at a time.** `file_put` demanded `seq == nextSeq` and threw the transfer away otherwise, which is correct only while the relay waits for each reply — change 8 tells the server to pipeline a window, and each frame is handled on its own goroutine, so uploads would have failed nondeterministically the moment it did. Chunks now wait for their predecessor and a redelivered chunk is answered without rewriting, proved by firing eight chunks from eight goroutines in shuffled order under `-race`. And `Shutdown` only cancelled, leaving the actual group kill to a goroutine that the process can exit before scheduling — it now sweeps synchronously, so the records are gone by the time it returns. The same round wired two error codes and one audit outcome that were defined and never emitted.
- **Green:** 163 Go tests (171 including subtests), 0 failures, clean under `-race` (`test:race`, its own script because the detector needs cgo while the release build is static; CI runs it beside `check`); `go vet` and `gofmt -l` clean. `pnpm install --frozen-lockfile` after a two-line lockfile addition (one importer entry), `pnpm format:check`, `pnpm typecheck`, and eslint with `--ignore-pattern '.claude/**'` at 0 errors and the same 2 pre-existing `DropdownMenu.tsx` warnings Cycle 25 recorded. `git diff --stat` shows no `Bin` file; `bin/` is gitignored.
- The 8a spike under `packages/trueforge/spikes/remote-computer/` is **left in place**: Section 10 and Cycle 25 both cite it as the committed evidence for the measurements, so deleting `client/` would falsify them.

**Lessons learned:**

- **Freezing the wire contract as committed fixtures, not prose, is what made parallel work safe.** Two agents writing two halves of a protocol from the same paragraph will diverge on exactly the things paragraphs are bad at: whether a field is absent or `null`, whether an error reply may also carry a result. Eleven files and a round-trip test settle all of it, and the server can assert against the same bytes.
- **`exec.Cmd.Wait`'s error is not where the exit code lives.** With `WaitDelay` set, a command that exited cleanly still returns `ErrWaitDelay` when a grandchild holds the pipes, and reading the code from the error reports 1 for a successful build. `ProcessState` is right in every case, including the signalled one.
- **Truncation has two seams, and only one of them is obvious.** Keeping a tail as well as a head means the join can split a multi-byte character at either end. Trimming both is three lines; trimming without a bound quietly eats binary output, which is why the loop stops at three bytes.
- **A prefix test on a path is not a containment test.** `work-evil` passes `strings.HasPrefix(path, "work")`, and a symlink inside the directory passes any purely lexical check. Resolving to the deepest existing ancestor and then `filepath.Rel` handles both, and handles a file that does not exist yet, which an upload always is.
- **Injecting the sleep is what makes a five-minute backoff testable.** The alternative is a test that either takes five minutes or asserts nothing. The whole close-code policy is one pure function over (kind, step, how long it lasted), and the socket tests only have to prove the classification.
- **Mount the package, not the repository root, when building in Docker.** A worktree's `.git` is a file pointing outside the mount, and Go's VCS stamping fails on it. `-buildvcs=false` and a narrow mount; the named module-cache volume is chowned to the invoking user so nothing root-owned is left in the tree.

**Avoid next time:**

- Don't put a Go package's tests under a top-level `tests/` directory to satisfy a rule written for TypeScript. Unexported symbols are unreachable from there, and `testdata` is already the convention for shared fixtures. Record the deviation where the rule is, rather than working around the language.
- Don't add a workspace package and then run `pnpm install` without `HUSKY=0` from a worktree: `prepare` runs husky, which writes `core.hooksPath` into the shared `.git/config` of the main checkout.
- Don't let a matrix job assume every package is a Node package. A Go entry needs its own toolchain step, and the aggregate `test` script that Windows runs needs to not grow one.
- Don't set a frame guard at the platform limit. JSON escaping of control bytes multiplies a capped output several times over, and the platform enforces the limit by closing the socket, so the request that crosses it takes every other request on that computer with it.
- Don't test the orphan sweep by killing the daemon. Recording the group and then calling the sweep directly against a live one is the same code path, deterministic, and finishes in two seconds.
- Don't write a concurrency test that drives one request at a time. Every file test fed chunks from a single goroutine, so a hard ordering requirement looked correct for as long as nothing exercised it — and the thing that would exercise it was already written down as a change for the other half of the phase.
- Don't pass a connection's context into work that outlives the connection. It reads as good hygiene and it silently inverted the guarantee the plan makes: every socket blip became a mass SIGKILL. The lifetime a piece of work needs is a design decision, not whichever context is in scope.
- Don't claim a boundary the code does not hold. The README said a compromised server "cannot lift any of it", while `env` could hand an allowed `git` a `GIT_SSH_COMMAND` and run anything. A deny list defeated by `r''m` is a speed bump, and saying so is what lets an operator size the run-as account correctly.
- **Don't document the other half's behaviour from your own reading of the contract.** Two of the four clauses written into this README as "what the server does" were right, one was right only for some failure modes, and one described a guarantee the server had deliberately chosen not to pay for. Asking the agent that wrote it to confirm the wording cost one message and caught both.
- **A denylist of "things that can run a program" has no end.** Three rounds of adding names — `PATH`, then `GIT_CONFIG*`, then `HOME`, `KUBECONFIG`, `RUSTC_WRAPPER` — is the signal to invert it. The allowlist is six names and two prefixes, and what it costs is one documented `--allow-env` for the two features that need one. The honest version of the claim is also shorter to write down.
- Don't compare paths as strings when the answer is a security decision. `filepath.Rel` is case-sensitive and half the filesystems in use are not, so the refusal that protects the credential was one capital letter from being bypassed on macOS. Device and inode are what "the same directory" means.
- Don't tighten an identity check with a signal the thing being identified is allowed to change. Adding argv to the sweep's pid-plus-start-tick check looked strictly safer and silently inverted it: a shell execs into a lone command, so the record said `/bin/sh -c sleep 400` and the process said `sleep 400`, and the sweep would have skipped the one case the whole mechanism exists for. Every existing test used a compound command, which a shell cannot exec into, so nothing caught it.
- Don't write a file straight to its destination. Chunk zero truncates whatever was there and a digest mismatch deletes it, so a failed upload destroys the file it was replacing — and the open follows a symlink planted after the path was checked. Temp file, fsync, verify, rename.

## Cycle 26 — Phase 8b server: remote computers on Workers (2026-09-21)

**Goal:** Build the server half of Phase 8b of `docs/remote-computers-plan.md` — tables, enrollment, the relay Durable Object, the provider, the agent allowlist, the admin API and the audit log — against a wire contract frozen in advance so the Go client could be written in parallel.

**What we did:**

- **Froze the contract first, in one owner.** The spike's protocol moved to `packages/trueforge/src/computers/protocol.ts` as Zod schemas with named `z.infer` types, minus the test-only `probe` op and plus `protocol_version: 1` on `hello`, and was published as `docs/remote-computers-protocol.md`. The client agent built against the document, not the code, and the two halves met without a single shape changing.
- **Ported the relay with the four corrections the spike earned.** `RemoteComputerDO` finds its current socket by a connection generation stamped into the socket attachment rather than by position; everything it must still know after an idle minute — generation, last-seen, the revoked flag, the tenant, `hello` — lives in storage; the pending entry is registered before the frame is written; and the staleness poll runs inside the waiting request rather than on an alarm. The 60 s alarm writes last-seen and nothing else.
- **Request ids are random.** The spike numbered them `<generation>-<counter>` with the counter in memory. After a hibernation that counter restarts at zero with the same generation, so a late reply from an orphaned command could settle an unrelated request with the wrong output. `crypto.randomUUID()` costs nothing and closes it.
- **Four tables behind one store interface**, implemented once for SQLite (which D1 reuses) and once for Postgres, with paired migrations on all three and a 25-case contract suite that runs against each. Codes and credentials are only ever stored as sha256. A code is single use with a fifteen-minute life, and a rotation also deletes every unused code issued before it — otherwise a code handed out a minute earlier still worked after the credential was revoked.
- **Tenant-wide computers with a per-agent allowlist**, as Section 9 decided. `resolveSandboxUsability` gained the computer and the agent's name and is the one place that decides; `validateAgentSpec` gained only an `agent_name`, so its five callers each grew one line. `SandboxUsability` gained a reason, because "unknown", "revoked", "not allowed for this agent", "inline agent" and "offline" were one boolean before. Only offline stays usable.
- **Fixed the three sites Section 10 named.** The turn runner no longer gates a computer on a sandbox image build that is not its own; the file-download route derives the computer from the reference the turn stored and re-checks the tenant; and the Workers integration answers about a computer before it asks whether the built-in sandbox is on, so a tenant that never enabled it still gets its machines.
- **A fake client on a real WebSocket.** 23 Workers tests drive enroll → connect → exec → a file round trip with the digest checked → revoke entirely through the deployed routes, plus a whole turn in which a saved agent with `sandbox.computer_id` runs its command on the machine, in that session's directory. The three security comparisons were mutation-checked by hand: flipping the relay's tenant check, the allowlist check, and the credential lookup each turned a test red.

**Findings:**

- **The relay, not the row, knows what the machine is.** `last_seen_at` and the machine facts are mirrored into D1 by a 60 s alarm, so the first turn after a connect read nulls and built its session directory under `/nonexistent`. The whole-turn test caught it. `resolveProvider` now asks the relay for its stored `hello` and falls back to the row, which is one extra RPC on a path that is about to talk to that object anyway.
- **Hono passes a 101 with a socket through `app.fetch` intact.** This was the biggest unknown in the plan and needed no workaround: the connect route is a plain `router.get` mounted in front of the admin shell, and the upgrade reaches the Durable Object with the headers the route added.
- **Rotate is not revoke.** Both close the live socket with 4401, which the client treats as terminal — correct in both cases, because the credential it holds is gone either way. But only revoke sets the relay's revoked flag; a rotated machine is expected back with the new code, and marking it revoked would have locked it out.
- **A turn-time refusal surfaces as an HTTP status, not a turn event.** The sandbox factory throws inside `SessionHandle.createTurn`, so `POST /api/v1/sessions/{id}/turns` answers 422 and no turn is created. `tests/unit/apis/turnHarnessErrorStatus.test.ts` already proved that path for the sandbox errors; the computer refusals ride it unchanged.
- **The frozen contract has no home path.** The session directory is derived from `run_as_user` and `os`. A machine whose `$HOME` is somewhere else needs a `home` field in protocol v2 — recorded in the plan rather than worked around.

**What the security review changed:**

- **A grant named an agent, and a name is not an identity.** Creating an agent is not an admin action, so an admin who granted "deployer" before it existed — or typoed it, or whose agent was later deleted — was handing the machine to whoever next created an agent with that name. The allowlist now keys on the agent's immutable id. The API still takes names, because that is what a person types, and resolves them server-side; a name nothing answers to is a 422 rather than a grant left waiting.
- **The enrollment race was real and the reviewer proved it.** The redeem batch's second statement guarded on the timestamp the first had written, so two redeems of one code in the same millisecond both matched and the loser overwrote the winner's credential — both dead, code burnt. Statement 1 now stamps the credential hash onto the enrollment row and statement 2 guards on that. The same rule went through every other chained write that was re-checking a timestamp.
- **A download could read anything on the machine.** The route checked the tenant but not the allowlist, and the path was unbounded — including the client's own credential file, which is enough to connect as the computer and collect other sessions' commands and git credentials. File transfers are now confined to the session directory and the route re-checks the allowlist.
- **`hello` was unbounded, and `run_as_user` becomes a path that reaches a shell.** A quote in it broke out of `mkdir -p '…'`. Bounds on every field, a POSIX-user pattern on that one, the path quoted rather than interpolated, and control characters stripped before anything reaches a log or the model.
- **Deleting a computer erased what ran on it.** The audit rows cascaded. They now outlive the machine — no foreign key, a denormalised name — until the 30-day sweep takes them, and an admin can read the whole tenant's.
- **One unreproduced flake, and a hardening it prompted.** On a single run of the two computer test files together, three allowlist refusals did not fire; the turn proceeded to sandbox init for an agent with an empty allowlist. Five later runs of the same pair, and of the whole pool, were clean, and neither file fails alone. The mechanism is unnamed, so nothing was shipped as a fix for it — but it did prompt pinning the computer store's D1 reads to `first-primary`, which is right on its own terms: every other store here takes replica reads, and this is the one that answers "may this agent use this machine". For whoever looks next: an _empty_ read returns no row and therefore refuses, so an empty allowlist cannot be what let it through. The suspect list is reads returning a row that should not match, not reads returning nothing.
- **A route that never ran.** `GET /api/v1/computers/audit` was registered after `/{computer_id}`, so the wildcard took it and it answered "no such computer". Every fixed path under that prefix is now registered first, and a test enumerates them rather than trusting the order to stay right.
- **The rate limiter failed closed.** A fault in the limiter object turned into a 500 on the only two routes a machine can reach, which is the opposite of what its own comment promised. It catches, logs and lets the request through.
- **The migrations were edited in place rather than added to.** That is safe only because `0005_computer.sql` has never been applied to any D1 database — production is on `0001` to `0004` — and the Kysely pair had not shipped either. Once `0005` is applied anywhere, the next schema change is a new numbered file.
- Also: one hello per connection rather than per frame, every operation audited from a `finally` with an outcome rather than only the successes, a checksum-verifying installer that refuses root and takes the code from the environment, and a per-address rate limit on the only two unauthenticated routes.

**Lessons learned:**

- **Freezing the wire before either half exists is what let two agents work at once.** The contract was written as a document with the constants, the close codes and the exact failure wording, and neither side had to guess. The only mismatch that surfaced was an error code spelling (`is_a_directory`, not `is_directory`), and it cost one line because the document listed the codes.
- **A fake client that does not heartbeat is not a fake client.** Without `ping` the relay fell back to the connect time, so any test that ran past twenty-five seconds looked like a suspended laptop. Modelling the contract's own obligations made three timing failures disappear at once.
- **Don't let a concurrency test wait out a deadline.** Holding four requests and letting them time out cost eleven seconds each and made the file forty seconds slower than the work in it. Letting the fake client answer on demand, and waiting on a condition rather than a fixed number of ticks, took the file from 180 s to 49 s and removed the flake with it.
- **Mutation-checking a security comparison finds the test that does not test it.** Breaking the credential lookup left the connect test green, because no computer existed in that test's database — the query had nothing to wrongly return. Enrolling one first made the test real.
- **A field on a hibernating Durable Object is a bug waiting for an idle minute.** The spike said so; porting the code without porting that rule would have reintroduced it, because the storage write looks like overhead until you have seen it fail.
- **"Keyed by name" is a design smell wherever names can be reused and anyone can mint one.** The allowlist read correctly in every test because every test used the happy path: grant, use, done. The hole only appears when you ask who else can create that name, and the answer was "any user", because creating an agent was never admin-gated. The fix was small; finding it was not.
- **A guard that ties two statements together by a timestamp is not a guard.** `updated_at = ?now` and `used_at = ?now` read like identity and are not: two callers in the same millisecond compute the same value. Every chained write now depends on something only this call could have written.
- **An audit log that records only successes is worse than none.** It says what happened and implies nothing else did. The refused read, the offline exec and the setup command were all invisible, which is exactly the set someone reviewing a machine would want.

**Avoid next time:**

- Don't type a shared route helper as `Hono` when every real caller passes an `OpenAPIHono`; the generic parameters do not line up and the only honest fix is the narrower type.
- Don't mount an admin shell before the unauthenticated routes that live under the same prefix. `use('*')` swallows them, and the failure is a 403 on a machine that has no session to show.
- Don't put a new server path behind the static-asset handler. `/install.sh` needs `SERVER_PATH_PREFIXES` and `run_worker_first` changed together, and a unit test already asserts they match — which is the only reason it was caught before a deploy.
- Don't add a field to `ServerPersistence` for something only one runtime uses. Threading it through `createServerRuntime` as `ComputersService | undefined` made the type say "this runtime cannot" and saved roughly thirty test literals.
- Don't put a server-side jail only on the path the agent uses. `exec` sees the whole machine by design, and it is tempting to conclude the file operations may too — but they are reachable from an HTTP route by a different caller under different rules.
- Don't assume a store method's doc comment survived the design it was written for. `countAgentAccess` said "any computer in this tenant" while taking a `computer_id`; the implementer flagged it rather than guessing, which is the right instinct.

**Most likely cause of the flake, found by the controller (2026-09-21):** the adversarial reviewer was running mutation checks in this same worktree while the implementer ran its tests. Its re-review mutated the allowlist refusal in `resolveComputer.ts` and reported exactly "allowlist: 3 failures", and it warned at the time that the worktree was being edited concurrently (uncommitted implementer edits at 21:41; the fixes were committed at 22:07). A test run that overlaps that mutation window sees precisely the recorded symptom: three allowlist refusals do not fire and a turn reaches sandbox init for an agent with an empty allowlist, once, never again, and never in either file alone. That explains why 30 consecutive runs, the isolation audit and the query audit all came back clean. It is an inference from matching counts and timing, not a captured log. Process fix: a reviewer that runs mutation checks must do so in its OWN worktree or copy, never in the implementer's live worktree.

**Known flake, investigated further (still open):** What was seen — once, running `remoteComputer.test.ts` and `remoteComputerTurn.test.ts` together, three allowlist refusals did not fire and a turn proceeded to sandbox init for an agent with an empty allowlist. No test name or exact assertion text was captured at the time, and none survives anywhere in this tree or its scratch notes. How often — one sighting; 30/30 clean on a fresh run of both files together afterward, and neither file has ever failed alone. What this pass checked and ruled out: test isolation (every case gets a fresh ULID computer/agent id via a per-file counter, `putAgentAccess`/`isAgentAllowed` are always scoped by that id plus `tenant_id`, and vitest-pool-workers' default per-test isolated storage means no D1 row or Durable Object write from one test is visible to the next, so a leftover grant, enrollment, or DO socket from an earlier case cannot explain it); and the product query (`isAgentAllowed` in both the SQLite and Postgres stores filters `computer_id`, `agent_id`, and `computer.tenant_id` in one query, and every caller — the turn runner, spec validation — supplies `agent_id` from a saved session or agent record, never from request input, so an undefined or empty agent id has no row to match). Conclusion: unexplained — neither a test-isolation bug nor a flaw in the allowlist query was found, so nothing was changed. How to recognise it again: a turn or `resolveComputerUsability` call treats an agent as allowed when its allowlist for that computer is empty, and only when both files run in the same vitest invocation. If it recurs, the one thing missing from every sighting so far is the actual test name and assertion text — capture the full log before it's gone.

## Cycle 25 — Phase 8a spike: a Go client and a relay Durable Object, measured live (2026-09-21)

**Goal:** Settle the four questions Phase 8a of `docs/remote-computers-plan.md` puts in front of remote computers — hibernating sockets under a pending caller, the message size limit, reconnect after eviction and deploy, and whether `resolveProvider` can take a `computer_id` — with numbers rather than argument, then go or no-go.

**What we did:**

- Built a throwaway spike under `packages/trueforge/spikes/remote-computer/`: a Go client (dial, `hello`, heartbeat, jittered reconnect, `exec`, `cancel`, chunked `file_put`/`file_get`, a `probe` op for frame sizes) and a two-object Worker — `RemoteComputerDO`, the relay, and `CallerDO`, which stands in for `SessionDO` by calling the relay over RPC from inside `alarm()`. Deployed it as `trueforge-computer-spike` on `workers.dev`, ran the client bare on this machine behind NAT and in a `busybox` container, took the measurements, then deleted the Worker.
- Go is not installed here, so everything went through `golang:1.23` in Docker with a user-owned named volume for `/go/pkg`. `linux/amd64` and `darwin/arm64` build from one source pass at 5,849,240 and 5,709,906 bytes — cross-compilation proven, and well under the 10 MB Section 7 assumed.
- Wrote Section 10 of the plan with the full evidence table and 19 concrete changes to Sections 4 to 8, and recorded the go verdict with its two caveats.
- Verified: `pnpm format:check`, `pnpm typecheck`, `pnpm workers:check` and repo-wide eslint all clean (the two `DropdownMenu.tsx` warnings are pre-existing). The spike carries its own `tsconfig.json`, so type-aware eslint resolves it without joining any package project, and it is excluded from the `trueforge` CI path filter. No binary is committed.

**Findings, with the numbers:**

- **Hibernation is aggressive and the socket does not care.** A constructor counter went 2 → 3 → 5 → 7 across 0/5/15/30/60 s idle gaps while the socket count stayed 1. `getWebSocketAutoResponseTimestamp` kept advancing through all of it, so heartbeats cost no wake and liveness is still readable afterwards.
- **The pending map is safe; nothing else in memory is.** An entry only exists while a caller's RPC is in flight, and that keeps the object loaded. The spike lost `hello` to a hibernation seconds after connecting, because it was a field.
- **The frame limit is exactly 33,554,432 bytes, and exceeding it closes the socket.** A 16 MiB payload rode a 22,369,661-byte message fine; 24 MiB produced `Message is too large: 33554491 > 33554432` and every in-flight request on that computer died with the connection.
- **A reset relay loses in-flight requests as an RPC rejection, not an offline outcome.** Forced eviction answered in 72 ms with HTTP `1101`. A deploy against an active object did the same and re-entered `CallerDO`'s alarm; a deploy against an idle one kept the socket, the generation and the next `exec`.
- **Offline detection beats the 35 s target by a wide margin.** 38 ms on `SIGKILL`, 39 ms on `SIGTERM`, 23.1 s when the host freezes with TCP still open. `revoke()` closed the socket in 118 ms, refused the next call in 20 ms, and the client exited instead of hammering.
- **Warm overhead is not a concern.** Twenty consecutive `uname -a` through the alarm-held caller: 42/43/44/63 ms min/median/mean/max, none lost, and the same call straight from the Worker was no faster. Four `sleep 3` ran in parallel at 3,063 ms and the fifth queued and finished at 3,091 ms.
- **5 MiB round-trips correctly at 1.7–2.1 MiB/s**, all four digests agreeing. The rate is round-trip-bound: 40 sequential chunk requests at about 120 ms each.
- **Verdict: go.** No fallback to HTTP long-poll. The real streaming and non-streaming turns could not be run — no browser access, and the production Worker was off limits — so the controller runs those before 8b closes.

**Lessons learned:**

- **A hibernating Durable Object is not a long-lived object with a cache.** The instinct to hold "the connected computer's details" in a field is wrong; it survives seconds. The rule that came out of it is narrow and worth keeping: only state whose lifetime is bounded by an in-flight RPC may live in memory. Everything else goes to storage on the write, not on a timer.
- **"Never throws across RPC" is a property of the callee, not of the call.** `request()` returns an outcome for every failure it can see, and the caller still got a rejection when the object underneath it was reset. Any port that promises not to throw needs the caller to wrap it anyway.
- **A 5 s liveness alarm across every connected computer would have been waste.** The object is already awake for the whole of a pending request, so the staleness poll belongs inside the request. That is the difference between one wake per computer per five seconds and none.
- **Test the freeze, not the kill.** `SIGKILL` closes TCP and the relay hears immediately — it proves nothing about a suspended laptop. `SIGSTOP` reproduces the half-open socket exactly, and it is the only case where the heartbeat threshold is load-bearing (23.1 s versus 0.04 s).
- **Deploys are not uniform.** An idle relay keeps its socket across a deploy; one holding a request loses it, and the caller's alarm re-enters. Measuring only the idle case would have produced a confidently wrong claim, which is what the first reading of the evidence was.
- **The reference implementation's bugs are cheap to avoid and expensive to inherit.** Resetting the backoff step on every open (two clients with one credential evict each other forever), never checking heartbeat replies (a half-open socket reads as connected), picking a socket by identity after a replacement close, and reporting exit 1 for a signalled command all cost a line or two each here.
- **A base image without a CA bundle fails silently and forever.** `busybox` loops on `x509: certificate signed by unknown authority` with textbook backoff, which looks like a network problem and is not.

**Avoid next time:**

- Don't measure a Durable Object's behaviour without an instance counter. `boots` in storage turned "I think it hibernated" into a number, and it is three lines.
- Don't let an alarm-driven test replay its work. Guard on stored state at entry and record the re-entry instead — otherwise a platform reset silently doubles the run and the numbers lie.
- Don't run a probe loop through `curl | head`; `head` exits, `curl` takes SIGPIPE, `pipefail` kills the script, and you lose the run that mattered. Redirect to a file and cut it afterwards.
- Don't reach for `pgrep -f` to count survivors of a command whose text you searched for — it matches the shell that is running the search. Check from outside the machine under test.
- Don't put a spike inside a published package without deciding, in the same change, what CI does with it: its own `tsconfig.json` so type-aware lint resolves it, a path-filter exclusion, and a note on why it needs no changeset.
- Run `build:gen` before eslint on a fresh checkout. Seventy-two "unsafe assignment of an error typed value" errors were nothing but missing generated catalogs.

## Cycle 24 — Phases I3 and I4: approvals, questions and schedule notifications in Slack (2026-09-21)

**Goal:** Close Phases I3 and I4 of `docs/integrations-slack-plan.md` — let a Slack thread approve a tool call or answer a question, and let a finished schedule run post itself to a channel — on both runtimes, up to but not including the live workspace test.

**What we did:**

- **A held turn is now something a channel can answer.** A turn ending `done` with `required_actions` goes through `readPendingAction`, which reads back the one `model.message` the action's `source_event_id` names and resolves each held call to a tool name and a redacted, truncated argument line. `DeliveryContent` gained `approval_request` and `question`; the Slack adapter renders them as Block Kit. A held turn is checked **before** its final text, because the model usually narrates the call it is about to make — posting only that narration would leave the turn waiting forever. The narration rides along as `intro`.
- **`POST /api/v1/integrations/{integration_id}/interactions`.** Slack posts `application/x-www-form-urlencoded` with the JSON in `payload` and signs the **raw form body**; the same `verifySlackSignature`, the same five-minute window, the same `team_id` check, `409` while pending. Answering a question is open to anyone already in the thread — they could have asked it by typing.

**Lessons learned:**

- **"One delivery per turn" was a constraint, not an observation.** `integration_delivery` was unique on `turn_id`, and I4 needs one schedule run in several channels. Nothing about the feature hints at a unique index; it surfaced only when the second rule's enqueue reported `enqueued: false`. Widening it then made `getPendingDelivery({ turn_id })` and `claimDelivery({ turn_id })` ambiguous, so both had to take the conversation too — a store-API change nobody would have predicted from "add notification rules".
- **A derived value is a hidden assumption.** The retry sweep recovered the session with `getByExternalId(toSessionExternalId(row.conversation_key))`, which is correct exactly while a delivery goes back to the conversation that produced it. A rule breaks that silently: the sweep finds no session, logs "no turn to report" and marks the row failed. Storing what the router already knew costs one column and removes the coupling.
- **The obvious idempotency key was the wrong one.** The brief suggested deduping on the action's `trigger_id` / `action_ts`, and every one of those is unique per click — so a double click would have passed twice and forked the session. What must be unique is the _thing being settled_, which is the held turn. That one key also serialises a text answer racing a button, which a click-shaped key could not.
- **A paused turn usually has text, and the text is not the answer.** The first cut kept the existing "final text wins" ordering, so a model that said "I'll restart the service now" before asking for approval posted that line and no buttons; the turn then waited forever with nothing to click. Ordering the pending check first, and carrying the narration as `intro`, fixes it without losing anything.
- **Slack signs the form body, not the JSON inside it.** An interaction is `application/x-www-form-urlencoded` with `payload=<json>`, and a fixture that signed the JSON would have passed against an implementation that verified the JSON — both wrong in the same direction. The suite has a case that signs the JSON and asserts the adapter refuses it.
- **`response_url` is a capability, so it needs a host check.** It arrives inside a signature-verified payload, which makes it trustworthy today; posting to whatever it names would still turn any future verification slip into an SSRF. Restricting it to `hooks.slack.com` costs three lines.
- **Approving cannot be recorded on the turn input.** `UserToolApprovalMessage` has `thread_id`, `tool_call_id` and `approval` and nothing else, and widening it is a `trueforge-core` change the plan does not allow. The Slack user id therefore reaches the agent only through the denial `reason`, and reaches people through the replaced message. Recorded as a deviation rather than quietly dropped.
- **Editing a `pnpm patch` by hand means recomputing `@@` counts across four files.** `pnpm patch` → edit the extracted package → `pnpm patch-commit` regenerates it correctly, and is the only sane way to add a field to the port once the patch already exists.
- **A `vi.mock` of the adapter registry can still hold the real adapter.** Cycle 16 concluded "a fake adapter must be injected by `vi.mock`, never through `fetch`", which is true of the _registry_ but reads as "no fake fetch". Mocking the registry to return `new SlackChannelAdapter({ fetchImpl })` gives a Workers test that exercises the real `chat.postMessage` body — which is how the "a rule posts at the top of the channel, with no `thread_ts`" assertion became possible at all.
- **The Workers D1 database is shared across a test file and nothing resets it.** Two schedule cases both named their schedule `nightly-report`, so the first case's integration rule matched the second case's run and the "posts nothing" assertion failed with a delivery from another test's integration. Every case needs its own schedule name.
- **A per-call button pair is not a per-call decision.** Core validates a resume as a _batch_: every pending approval and every pending client-side call must be settled in one send, or it throws `invalid_send_input`. Offering Approve/Deny per call read as obviously right and produced, for any turn holding two, a message whose every button was refused forever. The shape of the API decided the shape of the UI, and the only way to find that out was to run a resume through the real executor.
- **The mock model has to emit the shape, not just the tool.** `tools-<K>` returns one call per message, which never produces a turn holding two. The scenario that mattered emits K calls in a _single_ assistant message. And `require_approval_for_tools` turned out to be a per-MCP-server selector, not an agent-level one, so no built-in tool can be gated in a Workers test — the client-side path exercises the same core rule and was the reachable way in.
- **Escaping is not the converter's job here.** `toMrkdwn` escapes what it converts, but tool names, argument summaries and chosen option text never went through it: they were interpolated straight into blocks. A model-authored `<!channel>` in a tool argument would have pinged the channel from inside an approval request.
- **Redaction by key only reaches the top level.** `{"request":{"headers":{"Authorization":"Bearer sk-…"}}}` has no secret-looking top-level key, and the nested object was stringified whole. Redaction has to recurse, and also has to look at values — a credential under `note` is still a credential.
- **A redaction rule needs "leaves this alone" tests as much as "hides this" tests.** The first value-shape rule was "24+ characters, no whitespace, has a letter and one of `[0-9._-]`", which is also every file path, every URL and every hyphenated slug. Nothing failed, because the only prose case in the suite was short. On an approval message that argument line _is_ the decision, so `path: [redacted]` on every file operation means approving blind. The rule now excludes anything with `/` or `:` and requires both cases plus a digit, or a hex digest, and six realistic arguments assert they survive.
- **Review found three things the suites agreed with.** A plain reply on a held _approval_ fell through to a fresh `user.message` turn — the test's own name said "gets the busy notice" while its assertion said `started`, because the test had been written to match the code. A rule post for a held run offered approve/deny buttons whose click derives a conversation key the run's session was never keyed by, so every one of them was dead by construction. And `encodeActionValue` clamped the _encoded JSON_, so a long option produced a value that decoded to nothing — the "stays inside 2,000 characters" test passed while the button it described was dead. A length assertion is not a round-trip assertion.
- **Smaller traps.** A `channel: undefined` override hit the `=== undefined` default branch of its own fixture helper and silently kept the channel. `@eslint-react/no-array-index-key` is not enabled in this config, so the disable comment for it was itself the lint error. And `tsc --noEmit` over `src/` stayed clean through every store-signature change while five test tsconfig projects were red.

**Avoid next time:**

- Don't add a second consumer of an outbox without reading its unique index first. "At most one per turn" is enforced in SQL, and every method keyed on `turn_id` alone inherits it.
- Don't dedupe on the identifier of the click. Dedupe on the thing that can only be settled once, or a second click starts a second turn.
- Don't order "post the text" ahead of "post the decision" for a paused turn. The text is the model explaining what it wants to do, not a reply.
- Don't hand-write a signature fixture for a new content type; sign the exact bytes the request body carries, and add a case that signs the wrong thing.
- Don't hand-edit a `pnpm patch`. Re-extract, edit, re-commit.
- Don't reuse a name in a Workers test file: the D1 database is shared and nothing resets it between cases.
- Don't validate a resume input against a recording executor. It accepts whatever it is handed; the harness does not, and the difference was a feature that could never work.
- Don't interpolate model-authored text into a channel's markup language. Escape it at the boundary, in one helper, including the tool's own name.
- Don't redact secrets by top-level key. Recurse, look at value shapes too, and refuse to print arguments you could not parse.
- **Session metadata is not an audit trail.** It looked like the cheapest durable home for who approved — already there for the sender, already exposed. But it is a single latest-wins map that `PATCH /api/v1/sessions/{id}` opens to every tenant user, so the one property an approval record needs, that the subject cannot forge it, was the one it did not have.
- **An anchored pattern is not a redaction rule.** `^bearer\s` catches a value that _is_ a header and misses one that _contains_ one, and "skip anything with a separator" — added to protect file paths — handed back every URL with a credential in it. Matching anywhere, and cleaning URLs rather than skipping them, keeps both properties.
- Don't let two code paths each decide how to render the same row. The sweep rebuilt content the notifier had deliberately stripped; one shared predicate over the row removes the possibility.
- Don't store an audit record anywhere its subject can write. Check who can PATCH the field before calling it a record.
- Don't call I3 or I4 finished. Neither has spoken to Slack, and the live test now also has to cover updating an existing app from the regenerated manifest, since interactivity does not appear on an app created before it.

**Lessons learned:**

- One symptom, three independent bugs. The settings router gated every verb on `isDaytonaSettingsSupported()`; the catalog route served `sandbox-catalog.yaml` verbatim regardless of runtime; and the Workers integration answered `checkSnapshotStatus` and `isSandboxUsableWithoutStoredRecord` from the deploy var alone, so capabilities reported a sandbox Settings could neither show nor change. Fixing any one of them alone would have left the page broken.
- Third cycle on the same flag: Cycle 17 wrote it as `isLocalFallbackEnabled: () => false`, Cycle 18's live acceptance test found that rejects every sandbox-enabled agent spec, Cycle 19 renamed it to `isSandboxUsableWithoutStoredRecord` (`3e59dad0`). And making the stored record authoritative here immediately re-opened Cycle 18's drift in the _other_ direction: a record left behind by a deploy that had since dropped the var made the validator say "configured" while capabilities said "off".
- **Adding a shared method is not the same as having one source.** The first pass added `isSandboxConfigured` and pointed the validator at it — but left `GET /capabilities` computing its own answer from a status refresh plus the fallback flag. The two agreed on Workers, which is where the tests looked, and still disagreed on Node: a Daytona build that was `pending` gave capabilities `false` and the validator `true`, so a spec was admitted that the turn then rejected with 422. The claim only became true when the old flags were **deleted** from the port. If a second way to compute the answer still compiles, it is still two sources.
- A boolean helper does not narrow. `isNodeRunnableManifest` returning `boolean` left `record.manifest` as the full union after the early return, so the Daytona call failed to compile — and with `as` escapes banned there is no shortcut. It had to be a type predicate. Same family: the `PUT` handler returning `saved.manifest` types as `StoredSandboxProviderManifest` (which includes `truefoundry`) and fails the response schema; return the validated request manifest.
- Widening the manifest into a union rippled through every Daytona helper (`toDaytonaSandboxProviderInput`, `createDaytonaProvider`, `toDaytonaSandboxProvider`, and `toSandboxProviderFromRecord`'s return type). In `providerUtils.ts` the new schema type collides with the core class of the same name, hence the `DaytonaSandboxProviderConfig` import alias.
- `.openapi()` metadata rides through `.omit()`, so naming the Daytona object would have leaked its component name into the credential-free catalog entry. The shared fields live in an unnamed `DAYTONA_SANDBOX_PROVIDER_SHAPE` spread into two separately named schemas.
- Two test traps cost real time. Mounting `createCapabilitiesRouter` bare gives `SyntaxError: Unexpected token 'I', "Internal S"...` because `resolveRequestContext` needs the auth middleware. And `expect(screen.queryByLabelText(/API key/)).toBeNull()` fails even when no form opened, because `ConfigureSandboxForm` is always mounted and jsdom does not hide a `<dialog>` without `open` — assert on the `open` attribute and on the recorded request instead.
- `@truefoundry/assistant-ui-runtime`'s `SandboxConfig` requires the four Daytona interval numbers and `CreateSandboxRequest` requires an `apiKey`, so the adapter maps the built-in entry to zeros and an empty key and the section never renders those fields. A deliberate dent, recorded in Section 12: widen the shared package only if a second credential-free provider arrives.

**Avoid next time:**

- Don't express "is X configured?" as a parameterless boolean on a runtime port when the answer depends on tenant state. Make it a query that takes the store, and route every caller through it.
- Don't let a catalog endpoint answer from a static file when the runtime decides what can run. A catalog is part of the runtime's contract, not a constant.
- A deploy variable says "this feature is available here", not "this tenant wants it". Conflating them leaves nothing to show in Settings, no way to turn the feature off, and a capability endpoint that can only report a redeploy.
- Don't cover only the happy transition. "Off before, on after" passed under the buggy row-presence validator; the case that caught it was the record that outlives the deploy var.
- Reach for a type predicate before reaching for a cast — a `boolean` helper silently pushes you toward the `as` the repo bans.
- Grep for unused _exports_ after widening a schema; `noUnusedLocals` does not catch them. An exported `CatalogDaytonaSandboxProvider` alias nothing imported stayed green through typecheck, lint and every test until `1ecedc94` removed it.
- Don't leave a UI action wired to a port method with no backend route. `deleteSandboxProvider` sat omitted behind an explanatory comment, and the Remove button was dead the whole time.
- When you claim "one source", delete the other one in the same change. A shared method that the old caller is free to ignore proves nothing, and the tests you write will look where you already believe the answer is.
- A stub in a test that re-implements an integration's rules will pass whatever the integration does. The Workers agreement test copied the rules by hand, so it could not have caught the Node drift; it now drives `createWorkersSandboxIntegration` and `createNodeSandboxIntegration` directly. Where a real integration would reach the network (a `pending` Daytona build calls `getImageBuildStatus`), pick a record type that short-circuits — `failed` for Daytona, any status for the prebuilt TrueFoundry provider.
- Deleting a provider does not delete what it started. Removing a Daytona record drops the credentials TrueForge needed to clean up its sandboxes, so they run on until the provider's own auto-delete. Say so in the confirmation and the docs rather than implying a tidy teardown.
- A switch that changes meaning needs an upgrade note. `TRUEFORGE_SANDBOX_BACKEND` went from "sandbox on" to "sandbox offered"; an existing deploy silently loses its sandbox until an admin clicks Enable, and saved agents answer 422 in between.

**Goal:** Close Phase I2.5 of `docs/integrations-slack-plan.md`: fold connecting a Slack workspace into the Settings drawer, and have TrueForge generate the Slack app instead of asking people to build it by hand.

- **Cycle 20's own lesson did not go far enough.** It wrote "check what the constraint actually forbids" and still read the fixed slots as a wall. **Avoid next time:**

- Don't read "the upstream port has no extension point" as "this cannot be built". Check whether a patch can put the definition in its canonical home before designing around the gap.
- Don't design a connect flow from the fields you want to store. Find the order the platform forces first; here it decided the schema, the uniqueness key and the status column.
- Don't widen a verification exception past the one request that needs it. The unsigned branch answers `url_verification` on a pending integration and nothing else, and it must stay that narrow.
- Don't let a permission list live in prose once something generates from it. A stale scope table is harmless while a human retypes it and becomes the app's real grant the moment a manifest is built; keep the list in the module the code reads and have the docs describe it.

## Cycle 21 — Phase 7c: Code Mode over the container's egress (2026-09-18 to 2026-09-21)

**Goal:** Let an agent on the Cloudflare Workers runtime call its MCP servers from inside a sandbox command, the way it already can on Daytona, TrueFoundry and local — design it, build it, deploy it, and pass a live acceptance run. Done: it passed on 2026-09-21.

**What we did:**

- **Picked the egress route over a capnweb relay.** A relay would have meant a second protocol inside the container and a second thing to keep alive for a turn; the egress route reuses a path Computer already builds. `ComputerDO` moves from `egress: { mode: 'direct' }` to `{ mode: 'http-gateway', gateway }`, and `SandboxEgressGateway` — a `WorkerEntrypoint` exported at the Worker's top level so `ctx.exports` resolves it without a cast — answers the one hostname `code-mode.trueforge.internal` and passes every other request through as `fetch(request)`.
- **Two independent controls decide what a container may reach.** The gateway's props carry `sessionDurableObjectName`, set from `ctx.id.name`, which is the workspace's own `tenant_id:session_id`; a path, a header or a body naming another session is ignored, and a workspace that cannot name itself gets 503 rather than a guess. Inside the session, `CodeModeBridgeRegistry` hands out a token when a turn starts Code Mode and drops it when the turn ends, and a token the registry does not hold is refused with 401 before any dispatcher is consulted. The name decides which session; the token decides which turn of it.
- **`mcp_client.py` gained an HTTP bridge.** It picks its mode from the environment: `TFY_CM_HTTP_URL` plus `TFY_CM_HTTP_TOKEN` POST each request to the host, `TFY_NATS_URL` plus `TFY_NATS_SUBJECT_PREFIX` leave the Node path exactly as it was. The HTTP path is `urllib.request` on a worker thread, standard library only, so the image needs nothing new. Reply handling was duplicated between the two paths and is now one function, which is what makes both report a `caller` or `transport` fault in the same words.
- **The image starts through an entrypoint now.** `http-gateway` turns off direct internet, so Cloudflare terminates the container's TLS with a CA it mints per container at start time, which cannot be baked in. `workers/computer-entrypoint.sh` copies `/etc/cloudflare/certs/cloudflare-containers-ca.crt` into the trust store, runs `update-ca-certificates`, points `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` at the bundle for certifi users, and `exec`s `computerd`. Without it every HTTPS call from a sandbox, a skill clone included, would fail to verify.
- **Timeouts are bounded downward.** `TFY_CM_REQUEST_TIMEOUT_SECONDS` is capped at `SANDBOX_EXEC_TIMEOUT_SECONDS`, itself capped at two thirds of the 840 s alarm pass, and the host gives up at the same bound — so the client quits before the command waiting on it is killed, and a hung MCP server cannot hold the alarm.
- **Tests cover everything short of a real container.** `sandboxEgress.test.ts` drives forwarding, the workspace name from both a named and a cold-by-id object, and four refusals; `codeModeBridge.test.ts` the token lifecycle, malformed requests and the dispatch timeout; `sandboxTurn.test.ts` a whole turn whose workspace presents its token while the command runs, plus the token dying with the turn and a confusion case that puts another session in the path, two headers and the body. `mcp_client_http_test.py` runs the real client against a stub host inside the built image via `pnpm --filter @truefoundry/trueforge test:sandbox-image`.
- **Deployed on 2026-09-18** as Worker version `9e10a572-3299-4712-8976-e2ed03b65838`, after the remote D1 migration `0003_delivery_next_attempt.sql` (5 commands, 1.46 ms). `/healthz` answers 200 and `/api/v1/capabilities` answers 401 unauthenticated. The image rebuilt and pushed as `trueforge-computerdo@sha256:59d23276…`; `enableInternet` flips with the egress mode, so existing containers relaunch on their next command. **Only the gate is on that deploy** — the egress switch, the pass-through gateway and the CA entrypoint. **Lessons learned:**

- **Nothing built this cycle has met a real container.** Local containers still do not start on this machine, so every test is workerd or the image in isolation. Whether the gateway sees real container traffic, and whether ordinary HTTPS survives being intercepted, was the live deploy's to answer. It answered yes on 2026-09-21, three deploys after the first one.
- **A certificate minted per container cannot live in the image**, which is what forced the entrypoint. And failing to install it is a warning, not an exit: a container that refuses to start is reported only as "Container failed to start", so exiting there would trade a broken HTTPS call for a failure with no cause in it.
- **`unknown` does not cross Workers RPC.** `CodeModeReply.result` is `unknown`, so `SessionDO.dispatchCodeMode` returns the dispatcher's reply already serialized and a refusal as a status plus a message. The request crosses as text for the same reason, which had the side benefit of putting parsing and validation in one place.
- **A retry policy is about what the failure proves, not how bad it looks.** Only a refused connection or an unresolvable host prove nothing was delivered. A timeout, a reset or any HTTP status may mean the tool already ran, so they are reported and never retried — the same rule the NATS path already used.
- **The Python client can only be tested where its imports exist.** `mcp` and `pydantic` are in the sandbox image, not on the host, so the client's tests run inside the built image. That run also confirmed mcp 1.29.0 and pydantic 2.12.5 are already there, so no Dockerfile change.
- **A turn only opens a Code Mode channel when a command actually runs**, so the turn test saw no channel at all until the mock model gained a scenario that calls the sandbox exec tool.
- **A stray `.pyc` got committed**, caught only by reading the branch diffstat at the end: `packages/trueforge-core/src/core/sandbox/scripts/__pycache__/mcp_client.cpython-312.pyc` came in with `888a3fc4`, showing as a `Bin 0 -> 21602 bytes` line in a source directory — the same tell as cycle 20's binary `mrkdwn.ts`. Removed, and `.gitignore` now covers `__pycache__`.
- **Agents sharing a worktree share its index.** Staging one file and committing swept up another agent's staged removal of that `.pyc`, and an amend of this entry landed inside that agent's commit instead of its own. Nothing was lost, and the rebase onto `0cbddda5` redrew those commit boundaries. Commit by pathspec when a worktree has company.
- **A worktree-isolated agent cannot run bare `git`.** The hook rewrites it to `rtk git`, and the worktree guard refuses what it cannot read as git targeting this worktree. `/usr/bin/git` works.

- **A test that builds the thing it checks proves nothing about how the Worker builds it.** The gateway tests passed their own props, and the turn tests dispatched on their own registry, so the two wiring points that matter most, `ctx.id.name` and `SessionDO`'s bridge, could be broken without a failure. Running the reviewer's mutations was what showed it. The Workers test config now sets `TRUEFORGE_SANDBOX_BACKEND` as the deploy does, so the real objects are reachable in tests.
- **A client-side check is not a control when the client's credentials sit next to it.** The destructive-tool check lived only in `mcp_client.py`, and the token it sends is in the same environment.

**Avoid next time:**

- Don't give a live run to an agent that cannot reach an authenticated session. Two runs here stopped before their first probe: once at a Clerk consent screen, and once because the browser tool was not permitted. The third, run by the controller, passed.
- Don't assume a made-up hostname fails to resolve under `http-gateway`. `code-mode.trueforge.internal` resolved to `fd00::119:1` inside the container, and the interception caught it.
- Don't run a Python script inside a tracked source directory before `__pycache__` is ignored. A `Bin` line in a diffstat is the only warning you get.
- Don't assume the `mcp-client` CLI works because the import does. The module sits on the FUSE mount at `chmod 0555` with the PATH link at `/usr/local/bin/mcp-client`; if the mount drops the mode, the CLI half of the prompt's promise is broken while `from mcp_client import call_tool` keeps working. Item 4 of the live list exists for that.
- Don't plan a rewrite if HTTPS turns out not to survive interception. Computer routes `computer.internal` to `ComputerDO.fetch` in every egress mode, so the same client, token, registry and dispatcher work under `egress: { mode: 'direct' }` with a path match ahead of `backend.handleFetch`. Only the host match moves.
- Don't put an `unknown` on a value that has to cross an RPC boundary. Serialize at the boundary instead of discovering it in the types.
- Don't let the request decide which session it belongs to when the object that received it already knows its own name.

## Cycle 1 — Cloudflare Workers port plan (2026-09-15)

**Goal:** Plan how to run the TrueForge server on Cloudflare Workers (D1 as the database, Durable Objects for turn events and coordination, sandbox off) with the least rewrite and no copied store logic.

**What we did:**

- Wrote `docs/cloudflare-workers-port-plan.md` on branch `feat/cloudflare-workers-port`: a survey of what is and isn't portable, verified platform facts, target architecture (Worker `fetch` + `SessionDO` + singleton `SchedulerDO`), a D1 transaction strategy that covers every transaction site, Phases 0–5, and a CI backlog.
- Survey: the Hono app, Vercel AI SDK, remote MCP, OIDC (`openid-client`/`jose`) and the async-generator turn loop already work on Workers. What blocks the port: `better-sqlite3` transactions, file-based migrations, Redis Streams and pub/sub, detached turns and schedule runs, the `setInterval` scheduler, Node static serving, file-system work in `config.ts` at module load, and imports that reach `undici`, `@daytona/sdk` and `sandbox-runtime` through `app.ts` and the core barrel.
- Checked two of the three Phase 0 gates during planning: `process.env` population under `nodejs_compat` (Cloudflare docs) and D1 JSONB/STRICT support plus batch semantics (local `wrangler d1 execute`). The bundle dry-run gate runs as the first implementation step.
- Decided: turns always run inside `SessionDO` whether streamed or not; phase 1 turns don't survive DO eviction and an alarm watchdog freezes orphans; OIDC is required (no standalone auth); the Worker entry lives in `packages/trueforge/src/workers/` rather than a new package; CI changes are deferred to a backlog; the repo stays on pnpm for its lockfile and wrangler runs via `bunx`.
- Designed an `AtomicRunner` (`readGroup` + `batchWrite`) so better-sqlite3 and D1 share one set of SQLite-dialect stores under `db/sqlite/**`.

**Lessons learned:**

- D1 has no interactive transactions (`BEGIN` is rejected). `batch()` rolls back only when a statement _errors_. An `UPDATE ... WHERE guard` that matches 0 rows still succeeds, and later statements commit. Probed locally: a guarded no-op UPDATE followed by an INSERT still left the inserted row.
- A batch can't pass one statement's `RETURNING` into the next, so ids and `append_id` values have to be computed in JS before the batch.
- D1 Sessions API (`withSession('first-primary')`) gives sequential consistency, not a snapshot.
- Cron Triggers don't guarantee non-overlap, so a singleton DO alarm keeps one schedule controller per database.
- `sqlite_version()` is blocked on D1, so feature support has to be probed directly (`jsonb`, `jsonb_set`, `->>`, `STRICT` all work locally).

**Avoid next time:**

- Don't port a "`WHERE` guard, then unconditional inserts" pattern to D1. Every statement after the guard must be `INSERT ... SELECT ... WHERE EXISTS (row from statement 1)`.
- Don't copy SQLite stores into a `db/d1/` tree. Change the shared stores to use `AtomicRunner`.
- Don't let errors cross a DO RPC boundary as classes. `instanceof` mapping breaks, so return discriminated `{ ok, status, code }` results.
- Don't add a Kysely SQLite migration without a paired `migrations/d1/NNNN_*.sql` until the schema-diff CI job exists.
- Don't use `.dev.vars` for local Workers secrets; use `packages/trueforge/.env`.
